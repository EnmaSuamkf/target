Implementation plan

Local agents, optionally in Docker

Keep everything exactly where it is — hub and broker on 127.0.0.1, no cloud, no tunnel — and add one choice per workflow: run its agent directly on the host as today, or run it inside a Docker container on the same machine. Same hub, same steps, same chained session; only the process boundary changes.

1Where we are today

npm start runs two processes on loopback: the awb broker on 127.0.0.1:8890 and the hub on 127.0.0.1:8893. Creating a workflow creates its own dedicated hook (createAwbHook, hub/awb.ts:188) with its own sandbox workdir, and every step of that workflow resumes one harness session.

When a step is dispatched, the broker spawns the agent as your user, on your real filesystem: runClaude builds claude --resume <id> -p <prompt> and hands it to runHidden, which wraps it in flock on the workdir (adapters/spawn-runner/shared.ts:122-129). The "sandbox workdir" is a naming convention, not a boundary — a hook with bypassPermissions (hub/awb.ts:162) can do anything you can do.

2What is proposed

Add a per-workflow sandbox choice, made once at creation time and written into the workflow's hook:

  • host (default) — exactly what happens today. Nothing changes.
  • docker — the same claude invocation runs inside a container, with the repo and the harness state bind-mounted in from the host.

Crucially, the broker stays on the host. It does not move into the container; it shells out to docker run per job. That single decision is what keeps this plan small — the hub, the callbacks, the hook registry, the abort path and the progress watchdog all keep working without knowing Docker exists.

Why the container needs no network to the hub

In this design the container only runs claude. The broker captures its stdout on the host and posts the result to the hub itself. The container therefore needs outbound internet (to reach the model API) and nothing else — no port, no --network host, no host.docker.internal. This also keeps the broker's loopback check on callbackUrl (broker/dispatch.ts:27-43) satisfied without touching it.

3Pros and cons

What you gainWhat it costs
A real boundary around a permissive agent. bypassPermissions stops meaning "anything you can do" and starts meaning "anything inside this container and its mounts". This is the whole point. Mounts are the new blast radius. A container is only as contained as its bind mounts; mount your home directory and you have gained nothing.
Reproducible toolchain per agent. Pin node, python, whatever the repo needs, in an image, instead of whatever happens to be on the host. An image to build and maintain. Plus a first-run pull, and slower step start-up.
Opt-in and reversible. Default stays host; existing workflows are untouched, and the choice is per workflow. Two code paths to keep working. Every future change to the spawn path has to be considered twice.
The watchdog, abort, terminal and token panel all keep working — if the path rules in §5 are respected. They break silently if they are not. A mismatched path does not error; it just makes the hub blind. See §5.1.
A stepping stone. This is phase D of the cloud plan, done first and in isolation, where it is cheap to get wrong. Credentials cross the boundary. The simplest setup mounts your Claude Code credentials into the container. See §5.4.
Relationship to the cloud plan

This plan is deliberately a strict subset of docs/cloud-nodes-plan.html: no registered agents, no publicBaseUrl, no heartbeat, no API keys. It builds the container story on its own, on a machine where you can debug it — and if you later do the cloud split, phase D is already done and proven.

4Where it plugs in

The spawn adapter already separates what to run from how to run it. runClaude (adapters/spawn-runner/claude.ts:26-56) computes an argv and hands three things to runHidden: the binary, the args, and the cwd. Docker mode is a rewrite of the first two, leaving the third alone:

Because the rewrite happens below the hub, these keep working with no changes at all:

  • The workdir flock (shared.ts:122-129) still runs on the host against the same lockfile — so a host workflow and a docker workflow pointed at the same repo still serialize against each other.
  • Abort — registerRun records the host process-group leader (broker/dispatch.ts:153-155). With docker run in the foreground, a SIGTERM to that group stops the container too.
  • Hook registry, callbacks, the hub — the hook is still local, so inspectLocalHook, hookRuntime and the callback URLs are all unchanged.
Why docker run --rm, not docker exec

A long-lived container plus docker exec looks tidier but is worse here: killing an exec client does not reliably kill the process inside the container, which breaks abort; and it adds a container lifecycle to manage. With --rm the container is disposable because none of the state lives in it — the repo and the harness sessions are bind mounts on the host. That is also why this plan does not inherit the cloud plan's "containers must never be ephemeral" constraint.

5What has to be got right

5.1  The workdir path must be identical inside and outside

This is the one that will silently break things. The hub finds a run's transcripts by slugifying the workdir path string: 

// hub/transcript.ts:29-32
export function claudeProjectDir(workdir: string): string {
  const slug = workdir.replace(/[^a-zA-Z0-9-]/g, "-");
  return path.join(os.homedir(), ".claude", "projects", slug);
}

Mount the repo at a different path inside the container (/workspace, say) and Claude Code writes its transcripts under a different slug. Nothing errors. The hub simply finds no artifacts — and then probeStepProgress returns null, last_progress_at never advances, and every step is declared stalled after 10 minutes (hub/progress.ts:246), exactly the failure mode the cloud plan needs a heartbeat to solve. Here it is avoidable for free.

5.2  The harness home must land where the hub looks

Same problem, other half. claudeProjectDir resolves the base from os.homedir() of the hub process — and, unlike hub/notifier.ts:101, it does not honour CLAUDE_CONFIG_DIR. So either:

  • Simplest: bind-mount the host's ~/.claude into the container. Everything works untouched — but the container shares your personal Claude Code state, including credentials (§5.4), and its sessions mix with your interactive ones.
  • Cleaner: give each dockerized agent its own claude home on the host (~/.target/agents/<agent>/claude) and teach claudeProjectDir to take a base directory, the way notifier.ts already does for its own lookup. This is a small change and it removes the coupling for good.

Recommend the second, but only after the first has proven the rest of the pipeline end to end.

5.3  File ownership

A container running as root writes root-owned files into the bind-mounted repo, which then need sudo to clean up on the host — and the hub, running as you, may not be able to read parts of the transcript tree. Run the container as the host uid/gid (--user "$(id -u):$(id -g)") and make the image's home writable for that uid. Verify this in phase 0; it is the second most common way this setup fails in practice.

5.4  Credentials cross the boundary

The agent inside the container has to be authenticated. Mounting the host's ~/.claude brings .credentials.json with it — convenient, and it undercuts part of what the container is for, since a hostile prompt inside the sandbox can read them. A dedicated API key per agent, passed as an environment variable, keeps the blast radius to something you can revoke on its own. Decide this explicitly rather than inheriting it from the mount.

5.5  free-code, and the sessions-as-paths problem

For free-code the session id is an absolute .jsonl path (hub/awb.ts:141-143, hub/progress.ts:152-158), which the hub stores and later feeds back to --session. If that path is only valid inside the container, resume breaks the same way §5.1 breaks the watchdog. The path-identity rule covers it, but it is worth an explicit test. Scoping the first cut to runner: claude and adding free-code afterwards is a reasonable simplification.

6Work to do

Phase 0 — Prove it by hand (no code)

Before touching either repo, run the two commands the adapter would generate, by hand, against a scratch repo: 

docker run --rm \
  --user "$(id -u):$(id -g)" \
  -v /home/u/scratch:/home/u/scratch \
  -v /home/u/.claude:/home/u/.claude \
  -w /home/u/scratch \
  <image> claude -p "create a file called hello.txt" --output-format json
# → capture session_id from the JSON envelope, then:
docker run --rm … <image> claude --resume <session_id> -p "now append a line to it" …

Check, in order:

  1. the second run resumes the same conversation;
  2. ~/.claude/projects/-home-u-scratch/ exists on the host and its .jsonl files move while the run is in flight;
  3. files created in the repo are owned by you, not root.
Gate

All three must pass before writing any code. Each maps to a section above (§5.1/5.2, §5.1, §5.3), and each is far cheaper to diagnose at a shell prompt than through two layers of dispatch.

Phase C — The image

  • A Dockerfile with the agent CLI plus whatever toolchain the target repos need.
  • Non-root user, uid/gid overridable at run time (§5.3).
  • Documented as replaceable: the image is per workflow, so a Python repo and a Node repo can use different ones.

Phase D — Decouple the transcript base directory

The §5.2 cleanup: give claudeProjectDir a configurable base, give each dockerized agent its own claude home, and stop sharing your personal one. Left last on purpose — it is an improvement, not a prerequisite, and it is much easier to reason about once the pipeline is known to work.

7Success criterion

Two workflows on the same machine, at the same time:

  1. Workflow H with sandbox: host behaves exactly as it does today — this is the regression check that matters most.
  2. Workflow D with sandbox: docker runs three steps chained on one session, across three separate docker run --rm invocations.
  3. D's progress bar and idle indicator move while a step is running — proving the hub can see into the container's transcripts (§5.1, §5.2).
  4. A 15-minute step in D is not timed out.
  5. Aborting a running step in D actually stops the container, and the step can then be re-run with ▶.
  6. Files D creates in the repo are owned by your user.
  7. H and D pointed at the same repo serialize — one runs, the other shows queued.
  8. D's "open terminal" offers a command that actually resumes the conversation.

8Security model

Nothing is exposed to the network by this plan — the threat model is unchanged from today. What changes is containment of the agent itself, which matters because the prompt an agent executes is not always something you wrote carefully.

  • The container is only as good as its mounts. The one mount that must exist is the workdir. Every additional mount is a hole you chose.
  • Mounts must come from the hook, never from the event body. The hook is written by the hub; the body is whatever the caller posted. Deriving a mount from the payload would turn the webhook into arbitrary host filesystem access.
  • bypassPermissions becomes defensible. Today it is unbounded; in a container it is bounded by the mounts. That is the reason to build this.
  • Docker socket: never mount it. -v /var/run/docker.sock inside an agent container is equivalent to giving it root on the host.
  • Credentials — see §5.4; the convenient option is the weaker one.

9Execution order

  1. Phase 0 — prove resume, path identity and file ownership by hand.
  2. Phase A — the sandbox wrapper in awb (the only real logic).
  3. Phase B — the per-workflow choice in target, end to end to the UI.
  4. Phase C — a maintained image (can start as a throwaway during 0).
  5. Phase D — decouple the transcript base dir.

10Open questions

  • One image for everything, or per workflow? Per workflow is more flexible and costs nothing structurally — the image is just a hook field. Recommend allowing it from the start, defaulting to one.
  • Should bypassPermissions stop requiring acceptBypassRisk when the sandbox is docker? Arguably yes, and it would be a real incentive to use containers. Requires deciding that the container is trusted containment.
  • Resource limits — --memory, --cpus, --pids-limit. Cheap to add, and the main defence against a runaway agent. Worth doing in phase A rather than retrofitting.
  • Does the workdir stay a sandbox, or become a real repo? Containers make pointing an agent at a real checkout much more defensible. That is arguably the whole motivation, and it should be an explicit decision rather than a drift.
  • free-code in the first cut, or claude only? See §5.5.
