Letting agents create, delete, and modify workflows & steps

1.Goal & two contexts

Allow agents to create, delete, and modify workflows and steps programmatically — using the same hub API the UI and CLI already call — in both of these situations:

ContextExampleWhat must be available
A. Target workflow step Agent dispatched by awb on a running workflow Scoped tools + policy injected with the step (TCP + optional RCI)
B. Ad-hoc conversation New agent terminal session, Cursor app chat, or claude outside Target Global skill the agent always loads — not tied to a workflow dispatch

The first version of this plan focused on context A only. That is insufficient: opening a fresh CLI or Cursor conversation does not run through Target's dispatch pipeline, so workflow attachments never appear. Context B requires globally installed skills per detected runner — your original instinct was right for that case.

2.How Target works today

Core model

  • Each workflow owns one dedicated agent (an agent-webhook-bridge hook). Steps run sequentially on a shared harness session (--resume chained).
  • Three runtimes: claude, free-code, cursor (CLI binary agent). Installed runners are probed via GET /api/runners → availableRunners().
  • Full JSON API for workflow/step CRUD — see hub/server.ts route header.

Mechanisms that only apply during workflow dispatch (context A)

TCP (Tool Catalog Packs) — HTTP tools the hub runs for the agent. Attached TCP packs are listed in every dispatched step via tcpCatalogPreamble(), with a per-step POST /api/tcps/execute?stepId=…&token=… URL. The agent must send that request itself.

RCI (Resources Context Injection) — Markdown resources injected into the step prompt by resourcesCatalogPreamble(). Material lands under ~/.target/resources/<workflowId>/. Scoped to the workflow; not global.

Hub API (both contexts use this)

3.The ad-hoc conversation gap

TCP and RCI are injected only when Target dispatches a step (composeStepInput() in hub/runner.ts). If you open a new Cursor chat, run agent in a terminal, or start claude in a random directory, none of that injection happens — even if Target is running on the same machine.

For context B, the agent needs:

  • Knowledge — hub base URL, routes, auth, constraints (pending-only edits, context lock).
  • A way to act — shell/curl against the hub API with the admin Bearer token, or (later) a Target MCP server registered globally in the agent's MCP config.

A global skill installed into each detected runner's skill directory solves the knowledge problem and points the agent at the REST API. It does not replace TCP for workflow steps — the two layers serve different contexts with different security models.

  1. WebMCP on every UI action — document.modelContext.registerTool() in the React UI.
  2. Global skills per detected runner — when Target sees an installed CLI, ensure a Target management skill exists under that agent's skills directory; install if missing.

Revised verdict: global skills per runner — yes, for context B, via an explicit target sync-skills command (see §7). WebMCP — optional later for browser agents on the UI tab only; it does not reach CLI sessions.

5.Why WebMCP is not the main path

WebMCP registers tools on a web page for browser-resident agents. Target workflow agents are CLI processes spawned by awb — they never see document.modelContext unless you add browser automation as an extra hop.

6.Recommended hybrid approach

Context A

Target Management TCP pack

Bundled TCP attached to workflows that should self-modify during runs. Per-step execute URL + scoped token. Same tool set as before (add_step, delete_workflow, …).

Context A (optional)

RCI copy on workflow

Same policy skill attached via Resource Set for redundancy in long workflows — optional if TCP catalog + global skill already loaded in the same session.

Context B

Global skill: target-workflows

One skill per runner, synced by target sync-skills. Teaches hub REST API, auth from ~/.target/config.json, safety rules. Always available in ad-hoc chats.

Context B upgrade

Target MCP server (Phase 4)

Optional local MCP exposing the same operations as structured tools — registered once in ~/.cursor/mcp.json, Claude Code MCP config, etc. Better ergonomics than curl in a skill.

Example TCP tool (context A — add step)

{
  "name": "add_step",
  "description": "Add a pending step to a workflow.",
  "requestTemplate": "curl -sS -X POST 'http://127.0.0.1:8893/api/workflows/$WORKFLOW_ID/steps' \\
    -H 'Authorization: Bearer $TOKEN_1' \\
    -H 'Content-Type: application/json' \\
    -d '{\"description\":\"$DESCRIPTION\"}'",
  "inputs": [
    { "name": "WORKFLOW_ID", "description": "Workflow uuid", "required": true },
    { "name": "DESCRIPTION", "description": "Step task text", "required": true }
  ],
  "tokens": { "TOKEN_1": "<scoped or admin token>" }
}

Global skill content (context B — different auth path)

The global skill does not reference /api/tcps/execute (no step token exists outside a dispatch). It teaches:

  • Hub origin: default http://127.0.0.1:8893 (or read from env / config).
  • Auth: Authorization: Bearer <adminToken> from ~/.target/config.json.
  • Example: curl -H "Authorization: Bearer …" http://127.0.0.1:8893/api/workflows.
  • Policy: confirm before DELETE; respect pending-only edit rules; context lock after injection.

TCP tool set (unchanged)

Tool nameMaps to
list_workflowsGET /api/workflows
get_workflowGET /api/workflows/:id
create_workflowPOST /api/workflows
delete_workflowDELETE /api/workflows/:id
rename_workflowPATCH /api/workflows/:id/name
set_contextPATCH /api/workflows/:id/context
add_step … restart_workflowSame routes as §2 table

One skill, not one skill per action

Whether global or RCI-injected, a single target-workflows skill teaches policy and patterns. TCP (context A) or REST/MCP (context B) carries the per-operation parameter lists.

7.target sync-skills

Explicit, idempotent command — run from npm run target:install and available standalone. Does not run silently on every hub request. 

# Standalone or as part of install
node hub/cli.ts sync-skills
# or: npm run target:sync-skills

Algorithm

  1. Call availableRunners() — same probe as the create form (<binary> --version).
  2. For each runner where installed === true, copy the bundled skill from the repo to that runner's global skills path (see table below).
  3. Compare a TARGET_SKILL_VERSION stamp inside the installed copy with the repo's version; skip if identical, upgrade if older, never downgrade without --force.
  4. Print a summary: which runners synced, which skipped (not installed), which updated.

Install paths per runner

RunnerCLI binaryGlobal skill destination
cursor agent ~/.cursor/skills-cursor/target-workflows/SKILL.md
claude claude ~/.claude/skills/target-workflows/SKILL.md
free-code free-code ~/.free-code/skills/target-workflows/SKILL.md

Bundled source in repo: skills/target-workflows/ (one tree; small runner-specific frontmatter overrides if needed — e.g. Cursor vs Claude trigger wording). Paths follow each harness's existing skill discovery (same as Cursor's skills-cursor layout today).

Guardrails (addressing earlier concerns)

ConcernMitigation
Surprise writes under home dir Only runs during target:install or explicit sync-skills; logs every path written.
Conflicts with user skills Installs only under target-workflows/ subfolder; never overwrites unrelated skills.
Docker workflow steps Global host skill irrelevant inside container; those steps use TCP injection (context A).
Version drift TARGET_SKILL_VERSION in skill frontmatter; re-run sync after Target upgrade.
Runner not installed Skipped — no error. Matches "detect which agents could be used on target".

Uninstall: target sync-skills --remove deletes only the target-workflows folder from each detected runner's skills tree.

8.Architecture

9.Implementation plan

Phase 1 — Workflow tools (context A)

  1. Bundled TCP pack hub/bundled/target-management.tcp.json; import on install or first hub boot.
  2. UI preset: "Attach Target self-management" on workflow create.
  3. Tests: hub/tcp-acceptance.test.ts pattern for management tools.

Phase 2 — Global skills + MCP manifest (context B)

  1. Add skills/target-workflows/SKILL.md (+ optional reference docs) in the repo.
  2. Implement hub/sync-skills.ts + node hub/cli.ts sync-skills.
  3. Add mcp/runners.manifest.json (§12) + hub/sync-mcp.ts + sync-mcp CLI.
  4. Wire both into npm run target:install and re-check on npm start.
  5. Optional operator overrides: ~/.target/mcp-sync.json.

Phase 3 — Safer credentials

  • Scoped workflow-management token in ~/.target/config.json (rotatable from Settings).
  • Global skill references scoped token, not full admin, when available.
  • TCP step path: same-workflow mutation limits when authenticated via step token.

Phase 4 — Optional upgrades

  • Target MCP server — local stdio/HTTP MCP wrapping hub routes; target sync-skills --mcp writes MCP config snippets per runner.
  • In-process TCP executor — kind: "target-internal" avoids localhost HTTP loopback.
  • WebMCP on UI — thin wrapper over api/client.ts for browser-native agents only.

10.Security & scope

LayerAuthBlast radius
TCP in workflow step Per-step callbackToken; tools must be attached to workflow Low — can restrict to same-workflow mutations
Global skill (REST) Admin or scoped Bearer from config High — any workflow on the hub; skill must teach confirmation before destructive ops
Target MCP (future) Same as global skill; registered in agent MCP config High — same as REST; better structure, same power

Principle: use context A (TCP) for automated self-modifying workflows; use context B (global skill / MCP) for operator-driven ad-hoc sessions. Do not embed the admin token in workflow step prompts — step agents should use the TCP execute path only.

11.Optional future: WebMCP + Target MCP

Target MCP server (priority over WebMCP for CLI agents)

Cursor and Claude Code already load MCP servers globally. A small target-mcp package exposing list_workflows, add_step, etc. as MCP tools gives context B the structured ergonomics you wanted from WebMCP — without requiring a browser tab. target sync-skills --mcp can append the server entry to each runner's MCP config when detected. See §12 for the per-runner manifest; see §13 for when the hub must be running and what fails when it is not.

WebMCP on the UI (browser agents only)

For Gemini-in-Chrome or similar on 127.0.0.1:8893, register tools via document.modelContext wrapping api/client.ts. Feature-detect; no impact on CLI paths. Phase 4, lowest priority.

12.MCP config manifest per runner

What Target has today

No MCP runner manifest exists yet. The only persisted hub config is ~/.target/config.json (hub/config.ts): host, port, adminToken, timeouts, optional sandboxHost, modelContextWindows. It does not describe where each agent harness stores MCP settings or what to write there.

Target's workflow runners (PUBLISHABLE_RUNNERS in hub/awb.ts) are claude, free-code, and cursor only. Claude Desktop is a separate app — not a workflow runner — but it should still appear in the sync manifest as an optional fourth target for ad-hoc conversations.

Proposed: repo manifest + optional operator override

FilePurpose
mcp/runners.manifest.json (in repo) Canonical definition: one target MCP server entry + per-harness destination paths and merge rules. Shipped with Target; versioned in git.
~/.target/mcp-sync.json (optional) Operator overrides: disable a harness ("cursor": false), custom hubUrl, alternate command path to target-mcp, etc. Never committed.
~/.target/config.json (existing) Runtime values merged at sync time: host, port, adminToken → substituted into the MCP server's env block. Do not duplicate the token in the repo manifest.

Example mcp/runners.manifest.json

  "serverKey": "target",
  "server": {
    "description": "The Target Project hub — workflows, steps, run control",
    "command": "node",
    "args": ["{{TARGET_MCP_ENTRY}}"],
    "env": {
      "TARGET_HUB_URL": "{{HUB_ORIGIN}}",
      "TARGET_ADMIN_TOKEN": "{{ADMIN_TOKEN}}"
    }
  },
  "harnesses": {
    "cursor": {
      "runnerId": "cursor",
      "detect": { "binary": "agent", "probe": ["--version"] },
      "dest": { "file": "~/.cursor/mcp.json", "pointer": "mcpServers" }
    },
    "claude-code": {
      "runnerId": "claude",
      "detect": { "binary": "claude", "probe": ["--version"] },
      "dest": { "file": "~/.claude/settings.json", "pointer": "mcpServers" }
    },
    "claude-desktop": {
      "optional": true,
      "detect": { "configMustExist": true },
      "dest": {
        "file": {
          "linux": "~/.config/Claude/claude_desktop_config.json",
          "darwin": "~/Library/Application Support/Claude/claude_desktop_config.json",
          "win32": "%APPDATA%/Claude/claude_desktop_config.json"
        },
        "pointer": "mcpServers"
      }
    },
    "free-code": {
      "runnerId": "free-code",
      "detect": { "binary": "free-code", "probe": ["--version"] },
      "dest": { "file": "~/.free-code/agent/mcp.json", "pointer": "mcpServers" },
      "postSync": ["enableInFreeCodeMcpStatus"]
    }
  }
}

Placeholders ({{HUB_ORIGIN}}, {{ADMIN_TOKEN}}, {{TARGET_MCP_ENTRY}}) are resolved when target sync-mcp runs — from loadConfig() and the installed repo path (or packaged desktop app path).

Merge rules (idempotent sync)

  1. Read destination JSON (create file + {"mcpServers":{}} if missing, where safe).
  2. If mcpServers.target is absent → insert the resolved server block.
  3. If present and managedBy: "target" stamp matches manifest version → skip (already synced).
  4. If present but user edited (no stamp / different version) → skip unless --force.
  5. Never remove unrelated servers (GitHub, Slack, flowise, …).

Commands

node hub/cli.ts sync-mcp          # merge manifest into each detected harness
node hub/cli.ts sync-mcp --dry-run  # print paths + diff, write nothing
node hub/cli.ts sync-mcp --remove   # remove only mcpServers.target (our stamp)

Called from npm start (re-check, skip if up to date) and npm run target:install. Same idempotent pattern as sync-skills.

Why not put this only in ~/.target/config.json? Destination paths and merge semantics are product definitions — they belong in the repo manifest. Operator overrides (mcp-sync.json) and secrets (adminToken) stay under ~/.target/.

13.Follow-up: Target MCP needs the hub running

A common question once Target MCP is configured globally: if Cursor has the MCP entry but Target is not running, can I still create a workflow from the Cursor app? The short answer is no — not successfully. Configuration persists; connectivity does not.

What auto-config on npm start actually does

When Target starts, it can detect installed runners and write MCP config if missing (skip if already present):

  1. Probe runners via availableRunners() (same as the create form).
  2. For each installed runner, ensure a target-mcp entry exists in that harness's MCP config (e.g. ~/.cursor/mcp.json, Claude Code's MCP settings).
  3. If the entry is already there — skip (idempotent).

That only tells Cursor how to spawn the MCP server process. It does not keep the hub alive after you stop Target, and Cursor may need a restart to pick up config file changes.

Runtime dependency chain

ComponentRoleRequired for…
Target MCP server stdio/HTTP process Cursor spawns; proxies tool calls to the hub API Listing tools; forwarding requests
Hub (:8893) JSON API, auth, DB, hook registration Create/edit/delete workflows & steps
Broker (:8890) agent-webhook-bridge; dispatches steps to CLIs Start/run workflows (not strictly create-only)

The MCP server is a client of the hub, not a replacement for it. It must not read ~/.target SQLite directly — that would bypass validation, hook creation, and auth.

What happens when Target is stopped

StateWhat the user sees
MCP configured, hub up Tools listed; create_workflow succeeds via hub API.
MCP configured, hub down Cursor may still spawn MCP and list tools, but every hub call fails (ECONNREFUSED on :8893). Create workflow fails — this is expected.
MCP not configured No Target tools in Cursor at all.

Same as curl: a global skill that teaches curl http://127.0.0.1:8893/… fails identically when the hub is down. MCP improves ergonomics when Target is running; it does not remove the need to start Target first.

Recommended MCP behaviour (Phase 4)

  • On initialize / tools/list, ping GET /health. Cache result for a few seconds; expose hub URL in server metadata.
  • When hub is offline, still list tools (so Cursor does not hide them) but every tools/call returns a structured error: { "error": "target_hub_offline", "message": "Start Target with npm start — hub not reachable at http://127.0.0.1:8893" }.
  • Global skill target-workflows documents the same rule: check hub first; if MCP or curl fails with connection refused, start Target before retrying.
  • Optional CLI: target status (or read /health) that agents can suggest to the operator.

Auto-config timing: start vs install

TriggerWrites MCP config?Hub running?
npm run target:install Yes — sync-skills --mcp (config only) No — install does not start the hub
npm start Re-check / skip if present Yes — hub + broker up while process runs
User quits Target (Ctrl-C) Config remains on disk No — MCP calls fail until Target restarts

Design principle: Target MCP is an online interface to a local service. Treat "hub must be running" as intentional — document it, return clear errors, and optionally surface hub status in the MCP handshake. Do not pretend offline workflow creation works.

14.Summary

ApproachContextVerdict
Target Management TCP pack A — workflow steps Recommended. Scoped, works in Docker, proven pattern.
target sync-skills (global skill per runner) B — ad-hoc CLI / Cursor Recommended. Addresses the gap workflow TCP cannot reach.
mcp/runners.manifest.json + target sync-mcp B — MCP wiring To implement. Per-harness paths for Cursor, Claude Code, Claude Desktop, free-code.
Target MCP server B — upgrade Recommended Phase 4. Structured tools; requires hub on :8893 (see §13).
WebMCP on all UI actions Browser on UI tab Optional later; does not replace B for CLI agents.
Scoped token + same-workflow TCP limits A (+ B hardening) Recommended Phase 3.

Bottom line: use both layers. TCP for workflow automation (safe, injected on dispatch). Global skills via target sync-skills for any conversation where Target is not dispatching the agent. Same hub API underneath; different auth and discovery paths. WebMCP is a nicety for browser agents, not the core design.
