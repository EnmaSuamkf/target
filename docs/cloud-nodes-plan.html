Implementation plan

Cloud hub + dockerized local nodes

Today The Target Project runs entirely on one machine, on 127.0.0.1. This plan splits it in two: the hub (workflows, steps, judge, UI) moves to the cloud on a public URL, and the agents move into Docker containers on the operator's machine, reachable through a tunnel. You send work from anywhere; the work runs on your own hardware, in a sandbox, and never touches the host.

1Where we are today

npm start brings up two processes on loopback and opens a browser: the agent-webhook-bridge broker on 127.0.0.1:8890 and the hub on 127.0.0.1:8893. Everything else — the database, the agent's sandbox, the harness transcripts — is a file under the operator's home directory.

Creating a workflow creates its own dedicated agent: createWorkflow (hub/workflow.ts:439) calls createAwbHook, which registers a hook by writing ~/.agent-webhook-bridge/hooks.json and gives it a private sandbox workdir at ~/.target/sandboxes/<agentName>. One workflow, one hook, one workdir, one harness session that every step of that workflow resumes in turn.

What today does well

  • Zero configuration and zero exposure. Nothing listens off 127.0.0.1; the admin token is the only gate and it never leaves the machine.
  • The hub can see the agent working. Because the transcripts are local files, hub/progress.ts can stat them and tell a hung step from a slow one — that is what lets a legitimate 40-minute step survive.
  • Full local affordances. "Open terminal" reattaches to the exact session (hub/terminal.ts), the filesystem picker browses real directories, and each workflow gets its own isolated sandbox.

What today cannot do

  • Reach you anywhere else. Close the laptop and the UI ceases to exist. There is no way to queue work from a phone.
  • Let anyone else send work. There is one admin token and it is all-or-nothing; there is no notion of another submitter.
  • Bound what an agent can touch. The sandbox workdir is a convention, not a boundary: the agent runs as your user, and a hook with bypassPermissions (hub/awb.ts:162) can do anything you can.

2What is proposed

Cut the system along the line that already exists in the code — the hook URL — and put the two halves in different places:

  • The hub moves to the cloud. Public URL, persistent disk, always on. It keeps workflows, steps, the judge, retries, the manual-review gate and the UI. It stops creating hooks and instead references agents that already exist on a node.
  • The agents move into Docker containers on the operator's machine — one long-lived container per agent, each with its own volumes and its own awb broker, exposed through a tunnel. The container dials out; no inbound port is opened on the host.

This is agentmesh's phase-2 vision (agentmesh/index.html, agentmesh/PLAN.md §6) applied to workflows instead of loose jobs — with one constraint the container design must respect: a workflow chains one harness session across all its steps, so containers cannot be per-job and cannot be ephemeral.

3Pros, cons, and the cheaper alternative

This is not a free upgrade. It buys reach and containment, and it pays for them in observability and operational surface.

What you gainWhat it costs
Send work from anywhere. The hub is always up, so a workflow can be queued from a phone and picked up whenever the node is online. The hub goes blind. It can no longer stat the transcripts, so the progress watchdog stops working until the node reports in — see §5.3. Without that, every step dies at 10 minutes.
A real sandbox. Today's "sandbox workdir" is a convention; a container is a boundary. This is what makes exposing an agent to the network defensible at all. Local affordances are lost. "Open terminal" and resume-in-place cannot work against a remote container. The UI already hides them (hub/awb.ts:105,150), so they degrade rather than break — but they are gone.
More than one submitter. API keys, quotas and attribution become possible; today there is one all-or-nothing admin token. The broker is now on the internet. The shared secret becomes a real credential, and the cloud database holds it — compromise the hub and you can submit jobs to the node. See §8.
Room to grow. N agents, later N machines, without changing the model — the registry already knows which node is behind each agent. A whole new operational surface. Tunnel, containers, volumes, image rebuilds, and a host with a persistent disk. Today it is npm start.
Agent reuse. One configured agent can serve many workflows instead of accumulating one hook per workflow forever. Per-workflow isolation drops. N workflows on one agent share its workdir and container — see the phase A caveat in §6.

The cheaper alternative, and why it is not this

There is a much smaller version of "use it from the web": leave the hub local and expose it with a tunnel (cloudflared tunnel --url http://127.0.0.1:8893). agentmesh already does exactly this and it works — API keys, rate limiting and remote detection are implemented there (agentmesh/hub/server.ts:60-92, agentmesh/hub/db.ts:252+).

Be honest about the choice

If the goal is only "queue work to my own machine from my phone", option A does that with essentially no code and keeps the watchdog and the terminal working. Option B is worth it when you need the hub to survive the laptop being off, want a real sandbox around an agent with write or command permissions, or intend to let anyone else submit. Everything below assumes those are the goals.

4What we reuse unchanged

  • dispatchStep (hub/runner.ts:169) — it only does fetch(workflow.hookUrl) with x-webhook-secret and an optional sessionid header. Point hookUrl at a tunnel and it works as-is. This is the seam the whole plan hangs off.
  • The hook protocol — {jobId, input, callbackUrl, startedCallbackUrl} in, {result, session_id} back on the callback. Runtime-agnostic already.
  • The graceful-degradation paths for remote hooks: inspectLocalHook returns local: false (hub/awb.ts:75), hookRuntime returns all-null (hub/awb.ts:105), harnessResumeCommand returns null (hub/awb.ts:150) → the UI already hides the terminal and session-resume offers for remote agents. Nothing to do here.
  • The judge, retries, manual review gate, session chaining, status .md — all of it is transport-agnostic and stays put.

Both execution modes ride the same seam

A workflow can be executed two ways, and both keep working with a remote agent for free — because both funnel into dispatchStep, which is the one thing this plan re-points:

  • Run the whole workflow — startWorkflow (hub/workflow.ts:772). setStepSelection persists which steps were ticked, and the sequential engine advances across callbacks, dispatching only those.
  • Run one step on demand — runStep (hub/workflow.ts:1221), the ▶ button. It dispatches to the same agent and resumes the same shared session, so an on-demand run continues the same conversation. It stays outside the engine for ordering, and if the step has acceptance criteria its callback still goes through the judge.

Nothing in either path knows or cares where the hook lives. The manual-review gate (continueStep) and abortStep sit on top of both and are equally transport-agnostic — with one exception, see §5.4.

5What actually blocks this

5.1  Hook creation is local-only

createWorkflow (hub/workflow.ts:451) calls createAwbHook, which registers the hook by writing ~/.agent-webhook-bridge/hooks.json (hub/awb.ts:188). A cloud hub has no such file. The model has to flip from "each workflow creates its agent" to "each workflow picks a registered agent" — which is what hub/awb.ts:8-10 already anticipated for phase 2.

5.2  Callbacks point at loopback

hub/runner.ts:144,150 build both callback URLs from cfg.host:cfg.port = 127.0.0.1:8893. From inside a container that resolves to the container itself. Nothing works until this is configurable.

5.3  The idle watchdog kills every remote step at 10 minutes

hub/workflow.ts:120-124 documents the degradation honestly: a candidate with no local artifacts "finds no signal and times out on the idle clock exactly as the old wall clock did — the watchdog degrades, never blocks". That is a sound trade-off while remote hooks are the exception. In this architecture they are the rule, and the trade-off inverts.

Consequence

probeStepProgress returns null for every remote hook → last_progress_at never advances → stepActivity falls back to progressMs = startedAt (hub/progress.ts:246) → every step is declared stalled after stepIdleTimeoutMs (10 min), no matter how healthy it is.

Containers make this worse independently: the transcripts move inside the container's filesystem, so even a local hub could not stat them.

5.4  Abort silently stops killing the run

abortAwbRun (hub/awb.ts:256) opens with a local-only guard: 

const info = inspectLocalHook(hookUrl);
if (!info.local || !info.found || !info.name) {
  log(`abort: hook not local/found, skipping broker kill`, "warning");
  return false;
}

For a tunnelled hook inspectLocalHook returns local: false, so the broker kill is skipped. The step still settles as failed in the DB — but the agent keeps running in the container, holding the workdir flock. That is exactly the bug the abort feature was written to fix (hub/workflow.ts:1261 documents it: "the step showed failed but the orphaned agent kept running for hours"), silently reintroduced for every remote agent.

It also hits retryTimedOutStep (hub/workflow.ts:775), which calls abortAwbRun first precisely so the retry does not queue behind the zombie. On a remote agent the zombie survives and the retry queues behind it until it times out too.

Fix — small

The guard only exists to obtain info.name, and the name is already in the URL: abortAwbRun builds the abort endpoint by rewriting the hook URL's path (abortUrl.pathname = /hook/<name>/abort, hub/awb.ts:262-263). Parse the name from the URL for remote hooks instead of looking it up in the local config, and POST to the same origin — the shared secret already authenticates it. Keep the local lookup only as the "hook exists?" warning it is on a local hub.

6Work to do

Phase 0 — Session-persistence spike (do this first)

Before writing any hub code, prove the core assumption. Build a throwaway container with awb + claude and a named volume on ~/.claude, then:

  1. Fire a job with no sessionid → capture session_id from the callback.
  2. docker restart the container.
  3. Fire a second job with sessionid: <that id>.
Pass condition

The second run resumes the same conversation (claude --resume <id> -p, adapters/spawn-runner/claude.ts:37-38). If this fails, the whole design is wrong and everything below is wasted — target's value is the chained session, not the dispatch.

Also settle here: authenticate the in-container CLI with a dedicated API key per container (env var) rather than bind-mounting host credentials. Mounting the host's credentials into a container that executes untrusted prompts reopens much of the blast radius the container exists to close.

Phase A — Registered agents

New table (hub/db.ts, alongside the existing block at :169):

CREATE TABLE IF NOT EXISTS agents (
  name         TEXT PRIMARY KEY,
  hook_url     TEXT NOT NULL,
  secret       TEXT NOT NULL,
  description  TEXT NOT NULL DEFAULT '',
  runner       TEXT NOT NULL DEFAULT 'claude',
  enabled      INTEGER NOT NULL DEFAULT 1,
  created_at   TEXT NOT NULL,
  last_seen_at TEXT
);

workflows gains one nullable column, via the existing addWorkflowColumn migration helper (hub/db.ts:255): agent_ref TEXT — null means a legacy local workflow that owns its hook.

Schema trap

Do not reuse agent_name for this. It is UNIQUE (hub/db.ts:172), so two workflows sharing one registered agent would collide on insert — and sqlite cannot drop a constraint without rebuilding the table. Keep agent_name synthetic (<slug>-<shortid>) as today; it stays the key for the status .md path and the log lines. agent_ref carries the real binding.

hook_url / secret stay denormalized on the workflow row. They are copied from the agent at creation time, so dispatchStep needs zero changes.

Consequence for the two execution modes

Today a hook is 1:1 with a workflow, so createWorkflow gives each one its own sandbox workdir (targetDir()/sandboxes/<agentName>, hub/workflow.ts:449). Phase A makes it N:1 — several workflows on one registered agent — and that drops the per-workflow sandbox isolation: they now share one workdir inside one container.

Sessions stay separate (each workflow keeps its own lastSessionId), so the conversations do not bleed. But the guard in runStep (hub/workflow.ts:1226) only blocks steps of the same workflow — its comment, "they'd otherwise fight over the same hook/session", becomes half true. Two workflows on one agent can dispatch concurrently and will contend on the container's workdir flock: one runs, the other sits queued until it wins the lock, bounded by queuedTimeoutMs (6h). That is correct behaviour, but it is new — with 1:1 hooks it could never happen.

Decide explicitly: either bind one workflow per agent at a time (a busy flag on the agent row, rejecting a second binding), or accept the queueing and document that workflows sharing an agent share its files. Do not leave it implicit.

Phase B — Public callbacks

hub/config.ts: add publicBaseUrl: string | null. hub/runner.ts:144,150: replace the two hardcoded strings with a shared baseUrl(cfg) = cfg.publicBaseUrl ?? http://${cfg.host}:${cfg.port}.

Guards: in cloud mode, refuse to boot without a publicBaseUrl, and require https. The callback token still travels in the query string (?token=<callbackToken>) — acceptable over TLS, but it means access logs on any intermediary see it. Note it, revisit if a proxy is added. host also has to become bindable (0.0.0.0 or behind the platform's proxy); today it is hardcoded to 127.0.0.1 in the defaults (hub/config.ts:53).

The broker rejects it too

Changing the hub is not enough. The broker validates the callback URLs it is handed and drops any that are not loopback: if (url.protocol !== "http:" || !LOOPBACK_HOSTS.has(url.hostname)) (broker/dispatch.ts:38, with LOOPBACK_HOSTS = {127.0.0.1, localhost, [::1]} at :25). An https:// callback pointing at the cloud hub fails both conditions, so the node would run the step and then silently discard the result — the hub would see the step queued forever until queuedTimeoutMs.

This guard exists so a webhook caller cannot use the broker as a request proxy against arbitrary URLs, which is a real protection worth keeping. Replace it with an allowlist the operator configures (a callbackOrigins list in the broker's config, defaulting to loopback only), not with a blanket removal — the origin must stay something the node's owner chose, never something the request body chose.

Phase C — Progress heartbeat

Hub side. New route POST /api/steps/:id/progress?token=<callbackToken>, authenticated exactly like /started and /result (hub/server.ts:379,394). Body: { at?: ISO, kind: "transcript"|"session-file"|"run-log", token: string }. It reuses recordStepProgress and the same two guards as recordFreshSignal (hub/workflow.ts:88-95): an unchanged fingerprint is not progress, and a signal older than the stored one is ignored. Those guards are what keep the idle clock honest; a heartbeat that ignored them would just disable the watchdog.

Watchdog side. A workflow bound to a remote agent must not be judged by the idle clock until at least one heartbeat has arrived. In expireStale (hub/workflow.ts:134), a candidate with reason === "idle", an agent_ref, and last_progress_at IS NULL is skipped; only stepHardTimeoutMs applies to it. Once heartbeats flow, the normal idle logic resumes unchanged.

Node side. A small reporter loop in the container stats the same paths hub/progress.ts does (claudeTranscripts, freeCodeSessions, runLogs) and POSTs the fingerprint when it changes, every ~30s. It knows the step id because awb already receives jobId.

Phase D — The node image

Dockerfile + docker-compose.yml for one agent:

  • Node 24 base, claude (and/or free-code) installed, awb checked out, awb broker as the entrypoint.
  • Named volumes — this is the part that matters: ~/.claude (Claude Code sessions — without this, step 2 of every workflow cannot resume), ~/.agent-webhook-bridge (hooks.json, run logs, free-code sessions), and the workdir.
  • restart: unless-stopped. Never --rm.
  • Hook created once at container init (awb add), with the lowest permission mode that agent actually needs.
  • A cloudflared sidecar per container, or one tunnel plus a reverse proxy routing /<agent>/* to each container. Prefer the proxy once there is more than one agent.
flock changes meaning

runHidden serializes runs per workdir with flock (vendor/agent-webhook-bridge/adapters/spawn-runner/shared.ts:122-129). Across separate containers there is nothing to serialize and nothing to protect — the isolation is the container. But if you bind-mount the same host repo into two containers, you lose that serialization and flock will not save you. Mount a given repo into exactly one container.

The started callback still fires after the lock is acquired, so the queued → running transition and queuedTimeoutMs keep working untouched.

7Success criterion

A workflow created from the cloud UI, with three steps, bound to a dockerized agent through a tunnel, that:

  1. chains one session across all three steps;
  2. runs steps 1–2 through the sequential engine (mode 1), then step 3 via the ▶ button (mode 2), still on the same conversation;
  3. survives docker restart between step 2 and step 3 and still resumes;
  4. runs a 40-minute step without being timed out (heartbeats arriving);
  5. stops at a manualReview step until approved from the cloud UI;
  6. lets an aborted step actually die in the container, then be re-run with ▶;
  7. shows the terminal and session-resume offers hidden, not broken.

When that passes end to end, this is done.

8Security model

The risk inverts compared to tunnelling a local hub.

  • The exposed surface is now the operator's broker. A hook with bypassPermissions (hub/awb.ts:162) reachable from the internet is remote code execution — which is precisely why phase D is not optional.
  • The cloud box holds the keys to the machine. hook_url + secret sit in the cloud sqlite. Compromise the hub and you can submit arbitrary jobs to the node. Mitigate with: least-privilege permission mode per agent, Cloudflare Access with a service token in front of the tunnel (so the shared secret is not the only gate), and the manual review gate as a human checkpoint before anything touches a real repo.
  • Prompt payloads are untrusted input. That is the container's whole purpose — same stance as agentmesh/index.html:339.
  • Persistent disk required for sqlite (Fly volume / VPS / Render disk). Not serverless.

9Execution order

  1. Phase 0 — session-persistence spike. Nothing else starts until it passes.
  2. Phase A — registered agents (the model change; largest diff).
  3. Phase B — publicBaseUrl (small, but A is untestable end-to-end without it).
  4. Phase C — heartbeat (without it every step dies at 10 minutes).
  5. Phase D — the real node image + compose + tunnel.
  6. Phase E — API keys and the remote deny-list, before anyone else gets a URL.

10Open questions

  • Is option A enough? The single biggest decision in this document. If the real need is "queue work to my own machine from my phone", §3 says do that instead.
  • Multi-user? "So people can send me workflows" implies more than one submitter. That turns phase E from optional to mandatory and raises quota and attribution questions (agentmesh tracks submittedBy on a job — agentmesh/hub/db.ts:44).
  • One tunnel per container, or a proxy? Simpler vs. fewer moving parts at N > 2 agents.
  • Do containers get real repos bind-mounted, or only sandboxes? Real repos are the useful case and the dangerous one; see the flock caveat in phase D.
  • Does local mode stay? Recommended yes: mode: "local" keeps today's zero-config single-machine flow working, and it is what the tests exercise.
