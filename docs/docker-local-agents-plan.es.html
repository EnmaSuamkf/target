Plan de implementación

Agentes locales, opcionalmente en Docker

Dejar todo donde está — hub y broker en 127.0.0.1, sin nube, sin túnel — y añadir una elección por workflow: que su agente corra directamente en el host como hoy, o dentro de un contenedor Docker en la misma máquina. Mismo hub, mismos pasos, misma sesión encadenada; lo único que cambia es la frontera del proceso.

1Dónde estamos hoy

npm start levanta dos procesos en loopback: el broker de awb en 127.0.0.1:8890 y el hub en 127.0.0.1:8893. Crear un workflow crea su propio hook dedicado (createAwbHook, hub/awb.ts:188) con su propio workdir de sandbox, y todos los pasos de ese workflow reanudan una única sesión del harness.

Cuando se despacha un paso, el broker lanza el agente como tu usuario, sobre tu filesystem real: runClaude construye claude --resume <id> -p <prompt> y se lo pasa a runHidden, que lo envuelve en un flock sobre el workdir (adapters/spawn-runner/shared.ts:122-129). El "workdir de sandbox" es una convención de nombres, no una frontera: un hook con bypassPermissions (hub/awb.ts:162) puede hacer cualquier cosa que puedas hacer tú.

2Qué se propone

Añadir una elección de sandbox por workflow, tomada una sola vez al crearlo y escrita en el hook de ese workflow:

  • host (por defecto) — exactamente lo que pasa hoy. No cambia nada.
  • docker — la misma invocación de claude corre dentro de un contenedor, con el repo y el estado del harness montados desde el host.

Y lo importante: el broker se queda en el host. No se mete dentro del contenedor; hace docker run por cada job. Esa única decisión es lo que mantiene este plan pequeño — el hub, los callbacks, el registro de hooks, el camino del abort y el watchdog de progreso siguen funcionando sin enterarse de que Docker existe.

Por qué el contenedor no necesita red hacia el hub

En este diseño el contenedor solo ejecuta claude. El broker captura su stdout en el host y postea el resultado al hub él mismo. Así que el contenedor necesita salida a internet (para llegar a la API del modelo) y nada más: ni puerto, ni --network host, ni host.docker.internal. Esto además deja satisfecha la comprobación de loopback que el broker hace sobre el callbackUrl (broker/dispatch.ts:27-43) sin tener que tocarla.

3Pros y contras

Lo que ganasLo que cuesta
Una frontera real alrededor de un agente permisivo. bypassPermissions deja de significar "cualquier cosa que puedas hacer tú" y pasa a significar "cualquier cosa dentro de este contenedor y sus montajes". Este es el motivo de todo. Los montajes son el nuevo radio de explosión. Un contenedor solo contiene tanto como lo permitan sus bind mounts; monta tu home y no has ganado nada.
Toolchain reproducible por agente. Fijar node, python o lo que el repo necesite en una imagen, en vez de lo que haya en el host. Una imagen que construir y mantener. Más el pull inicial, y un arranque de paso más lento.
Opcional y reversible. El valor por defecto sigue siendo host; los workflows existentes no se tocan, y la elección es por workflow. Dos caminos de código que mantener vivos. Cada cambio futuro en el spawn hay que pensarlo dos veces.
El watchdog, el abort, la terminal y el panel de tokens siguen funcionando — si se respetan las reglas de rutas de §5. Y se rompen en silencio si no. Una ruta mal mapeada no da error; simplemente deja ciego al hub. Ver §5.1.
Un peldaño intermedio. Esto es la fase D del plan cloud, hecha antes y aislada, donde sale barato equivocarse. Las credenciales cruzan la frontera. El montaje más simple mete tus credenciales de Claude Code dentro del contenedor. Ver §5.4.
Relación con el plan cloud

Este plan es deliberadamente un subconjunto estricto de docs/cloud-nodes-plan.html: sin agentes registrados, sin publicBaseUrl, sin heartbeat, sin API keys. Construye la parte de contenedores por su cuenta, en una máquina donde puedes depurarla — y si más adelante haces la división cloud, la fase D ya está hecha y probada.

4Por dónde engancha

El adaptador de spawn ya separa qué ejecutar de cómo ejecutarlo. runClaude (adapters/spawn-runner/claude.ts:26-56) calcula un argv y le pasa tres cosas a runHidden: el binario, los args y el cwd. El modo Docker es reescribir los dos primeros, dejando el tercero intacto:

Como la reescritura ocurre por debajo del hub, esto sigue funcionando sin ningún cambio:

  • El flock del workdir (shared.ts:122-129) sigue corriendo en el host contra el mismo lockfile — así que un workflow host y uno docker apuntando al mismo repo siguen serializándose entre ellos.
  • El abort — registerRun registra el líder del grupo de procesos en el host (broker/dispatch.ts:153-155). Con docker run en primer plano, un SIGTERM a ese grupo para también el contenedor.
  • Registro de hooks, callbacks, el hub — el hook sigue siendo local, así que inspectLocalHook, hookRuntime y las URLs de callback quedan intactos.
Por qué docker run --rm y no docker exec

Un contenedor de larga vida con docker exec parece más elegante pero aquí es peor: matar al cliente de exec no mata de forma fiable el proceso de dentro del contenedor, lo cual rompe el abort; y añade un ciclo de vida de contenedor que gestionar. Con --rm el contenedor es desechable porque ningún estado vive dentro de él — el repo y las sesiones del harness son bind mounts del host. Por eso este plan tampoco hereda la restricción del plan cloud de que los contenedores no puedan ser efímeros.

5Qué hay que acertar

5.1  La ruta del workdir debe ser idéntica dentro y fuera

Esta es la que romperá cosas en silencio. El hub localiza los transcripts de una ejecución slugificando la cadena de la ruta del workdir: 

// hub/transcript.ts:29-32
export function claudeProjectDir(workdir: string): string {
  const slug = workdir.replace(/[^a-zA-Z0-9-]/g, "-");
  return path.join(os.homedir(), ".claude", "projects", slug);
}

Monta el repo en otra ruta dentro del contenedor (/workspace, por ejemplo) y Claude Code escribirá sus transcripts bajo un slug distinto. No falla nada. El hub simplemente no encuentra artefactos — y entonces probeStepProgress devuelve null, last_progress_at no avanza nunca, y todos los pasos se declaran stalled a los 10 minutos (hub/progress.ts:246), exactamente el modo de fallo que el plan cloud necesita resolver con un heartbeat. Aquí se evita gratis.

5.2  El home del harness debe caer donde el hub mira

El mismo problema, la otra mitad. claudeProjectDir resuelve la base desde os.homedir() del proceso del hub — y, a diferencia de hub/notifier.ts:101, no respeta CLAUDE_CONFIG_DIR. Así que o bien:

  • Lo más simple: montar el ~/.claude del host dentro del contenedor. Todo funciona sin tocar nada — pero el contenedor comparte tu estado personal de Claude Code, incluidas las credenciales (§5.4), y sus sesiones se mezclan con las tuyas interactivas.
  • Más limpio: dar a cada agente dockerizado su propio home de claude en el host (~/.target/agents/<agente>/claude) y enseñar a claudeProjectDir a aceptar un directorio base, como ya hace notifier.ts para su propia búsqueda. Es un cambio pequeño y elimina el acoplamiento para siempre.

Recomiendo la segunda, pero solo después de que la primera haya demostrado que el resto de la tubería funciona de punta a punta.

5.3  Propiedad de los ficheros

Un contenedor corriendo como root escribe ficheros de root dentro del repo montado, que luego necesitan sudo para limpiarse desde el host — y el hub, corriendo como tú, puede no ser capaz de leer partes del árbol de transcripts. Ejecuta el contenedor con el uid/gid del host (--user "$(id -u):$(id -g)") y haz que el home de la imagen sea escribible para ese uid. Verifícalo en la fase 0; es la segunda forma más habitual de que esto falle en la práctica.

5.4  Las credenciales cruzan la frontera

El agente de dentro del contenedor tiene que estar autenticado. Montar el ~/.claude del host se trae .credentials.json con él — cómodo, y socava parte de para lo que está el contenedor, ya que un prompt hostil dentro del sandbox puede leerlas. Una API key dedicada por agente, pasada por variable de entorno, mantiene el radio de explosión en algo que puedes revocar por separado. Decídelo explícitamente en lugar de heredarlo del montaje.

5.5  free-code y el problema de las sesiones-como-rutas

En free-code el id de sesión es una ruta absoluta a un .jsonl (hub/awb.ts:141-143, hub/progress.ts:152-158), que el hub almacena y luego devuelve a --session. Si esa ruta solo es válida dentro del contenedor, el resume se rompe igual que §5.1 rompe el watchdog. La regla de identidad de rutas lo cubre, pero merece un test explícito. Limitar el primer corte a runner: claude y añadir free-code después es una simplificación razonable.

6Trabajo a realizar

Fase 0 — Demostrarlo a mano (sin código)

Antes de tocar ninguno de los dos repos, ejecuta a mano los dos comandos que generaría el adaptador, contra un repo de pruebas: 

docker run --rm \
  --user "$(id -u):$(id -g)" \
  -v /home/u/scratch:/home/u/scratch \
  -v /home/u/.claude:/home/u/.claude \
  -w /home/u/scratch \
  <imagen> claude -p "crea un fichero llamado hello.txt" --output-format json
# → captura session_id del envoltorio JSON, y después:
docker run --rm … <imagen> claude --resume <session_id> -p "ahora añádele una línea" …

Comprueba, en este orden:

  1. que la segunda ejecución reanuda la misma conversación;
  2. que ~/.claude/projects/-home-u-scratch/ existe en el host y que sus .jsonl se mueven mientras la ejecución está en vuelo;
  3. que los ficheros creados en el repo son tuyos, no de root.
Puerta

Las tres tienen que pasar antes de escribir una línea de código. Cada una corresponde a una sección de arriba (§5.1/5.2, §5.1, §5.3), y cada una es mucho más barata de diagnosticar en un prompt de shell que a través de dos capas de dispatch.

Fase A — El sandbox docker en awb

Dos cambios pequeños en vendor/agent-webhook-bridge:

Deliberadamente no es un consumer nuevo (spawn:docker): el consumer elige qué CLI de agente ejecutar, y esto elige dónde se ejecuta. Mantenerlos ortogonales hace que ambos runners tengan Docker gratis y que broker/dispatch.ts:141 no se toque.

Fase C — La imagen

  • Un Dockerfile con el CLI del agente más el toolchain que necesiten los repos objetivo.
  • Usuario no-root, con uid/gid sobreescribible en tiempo de ejecución (§5.3).
  • Documentada como reemplazable: la image es por workflow, así que un repo Python y uno Node pueden usar imágenes distintas.

Fase D — Desacoplar el directorio base de transcripts

La limpieza de §5.2: dar a claudeProjectDir una base configurable, dar a cada agente dockerizado su propio home de claude, y dejar de compartir el tuyo personal. Va la última a propósito — es una mejora, no un prerrequisito, y es mucho más fácil de razonar una vez que se sabe que la tubería funciona.

7Criterio de éxito

Dos workflows en la misma máquina, a la vez:

  1. El workflow H con sandbox: host se comporta exactamente como hoy — esta es la comprobación de regresión que más importa.
  2. El workflow D con sandbox: docker ejecuta tres pasos encadenados en una sesión, a través de tres docker run --rm separados.
  3. La barra de progreso y el indicador de inactividad de D se mueven mientras un paso corre — demostrando que el hub ve dentro de los transcripts del contenedor (§5.1, §5.2).
  4. Un paso de 15 minutos en D no caduca.
  5. Abortar un paso en ejecución de D para de verdad el contenedor, y el paso se puede relanzar con ▶.
  6. Los ficheros que D crea en el repo son de tu usuario.
  7. H y D apuntando al mismo repo se serializan — uno corre, el otro muestra queued.
  8. El "abrir terminal" de D ofrece un comando que reanuda de verdad la conversación.

8Modelo de seguridad

Este plan no expone nada a la red — el modelo de amenazas es el mismo que hoy. Lo que cambia es la contención del propio agente, que importa porque el prompt que un agente ejecuta no siempre es algo que hayas escrito tú con cuidado.

  • El contenedor vale lo que valgan sus montajes. El único montaje obligatorio es el workdir. Cada montaje adicional es un agujero que has elegido.
  • Los montajes salen del hook, nunca del cuerpo del evento. El hook lo escribe el hub; el cuerpo es lo que haya posteado quien llame. Derivar un montaje del payload convertiría el webhook en acceso arbitrario al filesystem del host.
  • bypassPermissions pasa a ser defendible. Hoy no tiene límite; en un contenedor lo limitan los montajes. Ese es el motivo para construir esto.
  • El socket de Docker: no montarlo jamás. -v /var/run/docker.sock dentro de un contenedor de agente equivale a darle root en el host.
  • Credenciales — ver §5.4; la opción cómoda es la más débil.

9Orden de ejecución

  1. Fase 0 — demostrar a mano el resume, la identidad de rutas y la propiedad de ficheros.
  2. Fase A — el wrapper de sandbox en awb (la única lógica de verdad).
  3. Fase B — la elección por workflow en target, de punta a punta hasta la UI.
  4. Fase C — una imagen mantenida (puede empezar como algo desechable durante la 0).
  5. Fase D — desacoplar el directorio base de transcripts.

10Preguntas abiertas

  • ¿Una imagen para todo, o una por workflow? Por workflow es más flexible y no cuesta nada estructuralmente — la image es un campo más del hook. Recomiendo permitirlo desde el principio, con una por defecto.
  • ¿Debería bypassPermissions dejar de exigir acceptBypassRisk cuando el sandbox es docker? Se puede argumentar que sí, y sería un incentivo real para usar contenedores. Requiere decidir que el contenedor cuenta como contención de confianza.
  • Límites de recursos — --memory, --cpus, --pids-limit. Baratos de añadir, y la defensa principal contra un agente desbocado. Mejor en la fase A que retrofiteados después.
  • ¿El workdir sigue siendo un sandbox, o pasa a ser un repo real? Los contenedores hacen mucho más defendible apuntar un agente a un checkout de verdad. Eso es discutiblemente la motivación entera, y debería ser una decisión explícita y no una deriva.
  • ¿free-code en el primer corte, o solo claude? Ver §5.5.
