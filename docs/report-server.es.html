Plan de implementación

Reporte de actividad a un servidor central

Que cada instancia de Target envíe a un servidor central toda su actividad —workflows, steps, uso de tokens y conversaciones por workflow— para poder observar y monitorizar a los usuarios. La URL de destino se configura en un fichero .env, y cada reporte lleva la versión del cliente, que pasa a rastrearse en un CHANGELOG.md.

1Dónde estamos hoy

El hub de Target es un proceso Node (≥24) que vive en hub/, persiste en SQLite (~/.target/target.db, vía node:sqlite) y se configura desde ~/.target/config.json (hub/config.ts). Es mono-usuario: la tabla auth es un singleton (CHECK (id = 1)) y su existencia hace de flag de "setup completado".

  • Modelo de datos: tablas workflows y steps (más templates, settings, attachments, auth, sessions). Cada workflow tiene un agente/hook dedicado y una sesión Claude encadenada (last_session_id); cada step avanza de pending → queued → running → done|failed|waiting.
  • Dónde se asienta la actividad: onStepResult (hub/workflow.ts) es el punto por el que pasan todos los resultados de step; el fin de workflow ya emite una notificación (maybeNotifyWorkflowCompleted → hub/notifier.ts), y writeStatusMd / writeStepResults vuelcan el markdown de progreso.
  • Uso / tokens: hub/transcript.ts (readTokenUsage) y hub/tokens.ts ya derivan el consumo de tokens leyendo el transcript de la sesión.
  • Conversaciones: hub/conversations.ts ya sabe listar y resumir (listConversations, readConversationDigest) las conversaciones de una sesión.
  • Salida HTTP: el notifier ya hace fetch() saliente (a un MCP de Slack) con timeout — es el patrón que reutilizaremos para postear al servidor.
  • Bucle de fondo: hub/daemon.ts (startHub) ya corre un setInterval (expireStale) con unref() — el hueco natural para un flusher periódico.
Lo que falta

Hoy no hay ningún reporte saliente de actividad, ni soporte de .env (solo se leen variables sueltas como TARGET_HOME vía process.env), ni versión rastreada: package.json dice 0.1.0 en la raíz, en hub/ y en hub/ui/, y no existe CHANGELOG.

2Qué se propone

Cuatro piezas, cada una pequeña y desacoplada:

  1. Carga de .env: leer un fichero .env al arrancar el hub, sin dependencias nuevas, usando process.loadEnvFile() (nativo en Node ≥ 20.12/24). Ahí vive la URL de destino y el token del reporte.
  2. Versión + CHANGELOG: una única fuente de verdad para la versión (package.json), expuesta por hub/version.ts, y un CHANGELOG.md (formato Keep a Changelog) del que la versión sale. Todo reporte la incluye.
  3. Cola durable de eventos: una tabla nueva report_events donde el hub encola cada acontecimiento (workflow/step/uso/conversación) como JSON. Durable = sobrevive a reinicios y a cortes de red.
  4. Reporter (flusher): un módulo hub/reporter.ts que, en un intervalo del daemon, agrupa los eventos no entregados y los POSTea en lote a la URL del .env. Best-effort: si falla, reintenta; nunca bloquea ni tumba el motor de workflows.

3Configuración vía .env

Se carga un .env al inicio de loadConfig() (hub/config.ts), buscándolo primero en TARGET_HOME (~/.target/.env) y, si no, en la raíz del repositorio. Con Node ≥ 24 basta lo nativo, sin añadir dotenv: 

// hub/config.ts — al principio de loadConfig()
import { existsSync } from "node:fs";
for (const f of [path.join(targetDir(), ".env"), path.join(process.cwd(), ".env")]) {
  if (existsSync(f)) { try { process.loadEnvFile(f); } catch { /* .env inválido → se ignora */ } break; }
}

Nota de config

Los campos de reporte se leen del entorno, no de config.json, para que la URL y el secreto vivan solo en el .env (fuera de git) tal y como pide el requisito. El resto de config.json queda intacto.

4Versionado y CHANGELOG

Para "empezar a tener versión dentro de Target y reportarla" hace falta (a) una fuente de verdad y (b) un registro de cambios legible:

  • Fuente de verdad: el version de package.json de la raíz. Un módulo hub/version.ts lo lee (readFileSync + JSON.parse) y exporta TARGET_VERSION; así el reporte, la UI y los logs comparten el mismo número.
  • CHANGELOG.md en la raíz, formato Keep a Changelog + SemVer. Cada release mueve [Unreleased] a una versión fechada y actualiza el package.json. La feature de reporte entra como primera entrada.
  • Reportar la versión: todo lote de eventos y el heartbeat incluyen version. Así el servidor ve qué versión corre cada usuario.

5Qué se reporta: eventos y cola durable

Tabla nueva, creada junto al resto del esquema en hub/db.ts:

CREATE TABLE IF NOT EXISTS report_events (
  id           TEXT PRIMARY KEY,
  kind         TEXT NOT NULL,          -- p.ej. "step.done"
  workflow_id  TEXT,                    -- nulo para eventos globales (heartbeat)
  payload      TEXT NOT NULL,           -- JSON del evento
  created_at   TEXT NOT NULL,
  delivered_at TEXT,                    -- nulo = pendiente de entregar
  attempts     INTEGER NOT NULL DEFAULT 0,
  next_try_at  TEXT                     -- backoff exponencial en fallo
);
CREATE INDEX IF NOT EXISTS idx_report_pending
  ON report_events(delivered_at, next_try_at);

Los eventos son append-only e idempotentes: cada uno lleva su id (uuid), de modo que el servidor puede deduplicar un lote reenviado tras un fallo de red.

Regla de acoplamiento

emit() solo hace un INSERT local y vuelve al instante; si el reporte está desactivado (sin URL) es un no-op. La red vive únicamente en el flusher del daemon. Ningún fallo de reporte cambia el estado de un workflow.

7Contrato del endpoint

El contrato distingue dos nociones de "error", que antes se confundían:

  1. Errores del trabajo (un step o un workflow que falla): son datos que hay que reportar, viajan dentro del evento (objeto error). Ver §7.2 y §7.3.
  2. Errores del transporte (la ingesta rechaza o no responde): los gestiona el cliente con reintentos/backoff según el código HTTP. Ver §7.5.

7.1  Petición — envoltura del lote

POST {TARGET_REPORT_URL}
Authorization: Bearer {TARGET_REPORT_TOKEN}
Content-Type: application/json
Idempotency-Key: {batch_id}          # uuid del lote; permite reintento seguro
X-Target-Version: 0.2.0

{
  "batch_id": "b-uuid",              // == Idempotency-Key
  "instance_id": "a1b2c3…",
  "version": "0.2.0",
  "schema_version": 1,               // versión de ESTE contrato, sube si cambia
  "sent_at": "2026-08-09T12:00:00.000Z",
  "user": { "display_name": "Ada" },  // de la tabla auth; opcional
  "events": [ /* 1..N eventos, ver §7.2 */ ]
}

schema_version se separa de version (la del cliente) para que el servidor pueda evolucionar el formato sin romper instancias viejas. El tamaño de lote se acota (p.ej. 100 eventos / < 1 MB); si no cabe, el cliente parte el lote.

7.3  El objeto error (lo que faltaba)

Un step guarda su fallo como una cadena (steps.error), y onStepResult lo recibe como outcome.error. El contrato lo estructura para que el servidor pueda agrupar y diagnosticar, sin filtrar información sensible del transcript: 

"error": {
  "phase": "exec",                   // exec | judge — de qué job vino el fallo
  "kind": "agent_error",             // agent_error | judge_rejected | timeout |
                                     // queued_timeout | aborted | dispatch_failed
  "message": "…",                    // steps.error, recortado (p.ej. 2 KB máx.)
  "retryable": true,                 // ¿quedan reintentos? retry_count < max_retries
  "retry_count": 1,
  "max_retries": 2,
  "failed_criterion": "…",           // solo si kind=judge_rejected
  "started_at": "2026-08-09T11:58:00.000Z",
  "finished_at": "2026-08-09T11:59:58.000Z"
}

Ejemplo completo de un evento de fallo de step:

{
  "id": "e-77",
  "kind": "step.failed",
  "workflow_id": "wf-123",
  "session_id": "sess-abc",
  "created_at": "2026-08-09T11:59:58.000Z",
  "data": {
    "step_id": "s-9", "order_index": 2, "phase": "judge",
    "duration_ms": 41200, "retry_count": 2, "max_retries": 2,
    "error": {
      "phase": "judge", "kind": "judge_rejected",
      "message": "El resultado no crea el fichero pedido.",
      "retryable": false, "retry_count": 2, "max_retries": 2,
      "failed_criterion": "check that the plan is created",
      "started_at": "2026-08-09T11:58:00.000Z",
      "finished_at": "2026-08-09T11:59:58.000Z"
    }
  }
}

message se trunca (tope configurable) y respeta la política de privacidad: nunca se envían el secreto del hook, ni hashes de auth/sessions, ni el transcript completo salvo que TARGET_REPORT_INCLUDE_CONVERSATIONS=full.

7.4  Respuesta de éxito (con aceptación parcial)

La ingesta responde 200 con qué IDs aceptó. Así un solo evento corrupto no bloquea el lote entero (evita el "poison batch"): 

200 OK
{
  "accepted": ["e-77", "e-78"],
  "rejected": [
    { "id": "e-79", "reason": "schema", "detail": "data.order_index ausente" }
  ]
}
  • Aceptados ⇒ markDelivered (delivered_at fijado).
  • Rechazados por schema/permanente ⇒ se marcan como descartados (no se reintentan eternamente) y se registra en el log local — son bugs del cliente, no fallos de red.
  • Un id ya visto ⇒ el servidor lo devuelve en accepted (idempotente); si un lote entero se repite, basta la Idempotency-Key.
  • Un 200 sin cuerpo ⇒ se interpreta como "todo aceptado" (compatibilidad con un receptor mínimo).

7.5  Errores de transporte — qué hace el cliente

RespuestaSignificadoAcción del reporter
200OK (posible aceptación parcial)Marcar entregados; descartar rechazos permanentes
400 / 422Lote/JSON inválidoNo reintentar el lote tal cual: descartar (o poner en cuarentena) y loguear — es un bug, reintentarlo sería un bucle
401 / 403Token ausente o inválidoPausar el reporte y avisar en el log (config errónea); no quemar reintentos
404URL mal configuradaIgual que 401: pausar + log
409Duplicado (idempotencia)Tratar como entregado
413Lote demasiado grandePartir el lote a la mitad y reintentar
429Rate limitRespetar Retry-After; si no viene, backoff exponencial
5xxFallo del servidorReintentar con backoff exponencial + jitter
timeout / redAbortSignal.timeout() o fetch rechazaIgual que 5xx: attempts++, fijar next_try_at
Backoff y retención

El backoff crece por attempts (p.ej. min(2^attempts · 1s, 5min) con jitter), guardado en next_try_at de report_events. Los 4xx permanentes no reintentan (evitan el bucle de veneno). Los eventos entregados se purgan pasado un tiempo; los pendientes tienen un tope de antigüedad/cantidad para que un servidor caído no llene el disco.

8Privacidad y seguridad

A tener en cuenta

Las conversaciones pueden contener información sensible (rutas, secretos, código). Reportar su texto completo es una decisión con peso legal/de privacidad, no solo técnica.

  • Conversaciones configurables: TARGET_REPORT_INCLUDE_CONVERSATIONS con off / digest (por defecto, solo metadatos y resumen) / full.
  • Secretos: la URL y el token viven en .env (git-ignored); jamás se escriben en config.json ni se devuelven por la API. El X-Webhook-Secret de cada workflow y los hashes de auth/sessions nunca se reportan.
  • Transporte: se exige https:// para TARGET_REPORT_URL; si es http no-loopback, se avisa en el log.
  • Best-effort, no bloqueante: el fetch lleva AbortSignal.timeout(); un servidor caído solo hace crecer la cola, con un tope de retención (p.ej. purgar entregados y capar pendientes muy viejos).
  • Interruptor claro: sin TARGET_REPORT_URL o con TARGET_REPORT_ENABLED=false, no se emite nada.

11Criterio de éxito

Definición de hecho

Con un .env que fija TARGET_REPORT_URL, al usar Target normalmente el servidor recibe lotes que cubren toda la actividad —altas/cambios de workflow, cada transición de step, usage.snapshot por sesión y conversation.snapshot según la política de privacidad— cada uno con instance_id y version. Sin URL, no se emite nada y el hub funciona igual que hoy. La versión sale del CHANGELOG.md / package.json y se reporta en cada lote.

12Preguntas abiertas

  • Identidad de usuario: ¿basta instance_id + display_name, o el servidor asignará credenciales por instancia?
  • Conversaciones full: ¿se permite en algún caso, o se limita a digest por política?
  • Free-code / sandbox Docker: confirmar que el .env y el transcript quedan accesibles cuando el agente corre en contenedor (ver plan de agentes locales/Docker).
