1. Executive summary

Yes — this is possible feasible, and it is a moderate-sized but well-bounded change. The hub already treats "one step = one dispatch = one turn on the shared Claude session", so "the context is its own step that runs before every other step" is expressible in exactly the vocabulary the engine already speaks. Nothing about the runner, the awb hook protocol, the session-resume chain or the result-callback pipeline has to be reinvented.

The catch is not feasibility, it is blast radius. Steps are counted, numbered, selected, reset, timed out, judged, progress-barred and written to disk as <NN>-<slug>.md — so a new row at the front of the list touches a dozen read paths that all assume "every step is a task the operator wrote".

Recommendation: add a kind column to the steps table ('task' | 'context') and materialise a single auto-managed kind='context' step per workflow, pinned at order_index = -1 (not 0). The negative index is the load-bearing detail: it sorts first for ORDER BY order_index and for nextPendingStep, while renumbering nothing — so stepResultFileName keeps producing the same 01-…md, 02-…md names for existing steps and steps.at(-1) (the completion notification's "the workflow's result") still means the last task step.

The change is strictly additive if done as planned: a workflow with no conversation context and no context images gets no context step and behaves byte-for-byte as it does today, and the existing prepend path stays in place as the fallback for any workflow that has no materialised context step.

Estimated shape of the work: ~6 hub source files, 4 UI files, one new schema column, one new engine helper (reconcileContextStep), and a new test file alongside the existing hub/context.test.ts. No new HTTP route is strictly required.

2. Investigation findings

2.1 Where the context lives and how it is injected today

The context is a workflow-level column, not a step-level one.

  • hub/db.ts:250-251 — the workflows table carries conversation_context TEXT and context_injected INTEGER NOT NULL DEFAULT 0. Both are also added defensively for older DBs by addWorkflowColumn at hub/db.ts:353-354.
  • hub/db.ts:59-115 — interface Workflow, fields conversationContext and contextInjected.
  • hub/db.ts:615 — setWorkflowConversationContext(), the low-level setter; hub/db.ts:556 — setContextInjected(), the guard.
  • Context images are separate: attachments rows with field = 'context' and step_id = NULL — hub/db.ts:1624-1626 (AttachmentField), read via listFieldAttachments(workflowId, null, "context") hub/db.ts:1707.

The injection itself is a string prefix built at dispatch time — there is no persisted "injected preamble" anywhere:

  • hub/runner.ts:147 — contextPreamble(context, images, afterCompaction) builds the blob. hub/runner.ts:161 is the literal the user is describing: 
    return `${lead}Conversation context — this background applies to every step
of this workflow:\n\n${body}${section}\n\n---\n\n`;
  • hub/runner.ts:215-275 — composeStepInput() is the single place all three attachment-bearing inputs meet. At hub/runner.ts:251-257 the preamble is computed, and at hub/runner.ts:269-274 it is concatenated in front of step.description, the description images, the criteria note, the step-results note and the subagent suffix.
  • hub/runner.ts:332 — const freshConversation = sessionToResume === null;
  • hub/runner.ts:379 — the decision itself: 
    injectContext: mode === "exec" &&
  ((freshConversation && !workflow.contextInjected) || afterCompaction),

So today "before all" is implemented as "first N bytes of the first exec dispatch's input". The guard is closed elsewhere: chainSession() at hub/workflow.ts:620-636 sets context_injected = true the first time a session id is chained, and only when there actually is a context (text or images). restartWorkflow resets it at hub/workflow.ts:1048.

Once injected, the context is frozen: setConversationContext throws "context already injected" hub/workflow.ts:648-661, the route returns 400 hub/server.ts:992-1013, attaching a context image is refused the same way hub/server.ts:~1050, and the UI renders the textarea read-only hub/ui/src/views/ContextPanel.tsx:40, 84-89.

2.2 How a step is modelled and persisted

  • hub/db.ts:260-289 — the steps table. Ordering is a plain order_index INTEGER NOT NULL with CREATE INDEX idx_steps_workflow ON steps(workflow_id, order_index). Identity is the UUID id; order_index is explicitly documented as "an ordering, not an identity" at hub/db.ts:692-693.
  • hub/db.ts:117-203 — interface Step. There is no kind/type column today. I grepped for it; the only kind in the schema is last_progress_kind (the watchdog artifact type).
  • hub/db.ts:661-754 — insertStep(). Appends at MAX(order_index) + 1, or with afterOrderIndex inserts at afterOrderIndex + 1 and shifts every row >= that index down by one.
  • hub/db.ts:761 — listSteps() is ORDER BY order_index, unfiltered.
  • hub/db.ts:778 — nextPendingStep() is status = 'pending' AND selected = 1 ORDER BY order_index LIMIT 1. This is the whole scheduler.

2.3 Do special step kinds already exist? (Important — the answer is "no")

Key finding

There is no existing precedent for a special step kind to copy. The two features that look like they might be one are not:

  • The acceptance-criteria judge is a phase, not a step. StepPhase = "exec" | "judge" hub/db.ts:35 is a column on the same step row. onStepResult routes on step.phase hub/workflow.ts:1174 and dispatchStep(step, wf, cfg, log, {mode:"judge"}) reuses the same step id and callback token. No second row is ever created.
  • Manual review is a flag, not a step. Step.manualReview hub/db.ts:152 plus the waiting status.

So this change introduces the first real step kind. That means there is no established pattern to imitate — but it also means kind is genuinely new information the schema does not already encode some other way, which is the honest justification for adding a column.

2.4 How a step executes end to end

  1. advance() hub/workflow.ts:936-967 — the only "what runs next" decision. Refuses if the workflow is not running, if any step is running/queued/waiting; otherwise takes nextPendingStep() and dispatches it. If there is none and nothing is pending at all, it settles the workflow completed or failed.
  2. dispatchStep() hub/runner.ts:293-421 — builds the input via composeStepInput, then POSTs {jobId: step.id, input, callbackUrl, startedCallbackUrl} to workflow.hookUrl with an optional sessionid header. Marks the step queued on a 2xx.
  3. The broker answers {ok:true} immediately and posts back to /api/steps/:id/started hub/server.ts:471 then /api/steps/:id/result hub/server.ts:486.
  4. onStepResult() hub/workflow.ts:1146-1221 — keyed on the step id: const step = getStep(stepId); if (!step) return;. Chains the session, then either judges, holds for manual review, or completes and calls advance().
  5. writeStatusMd() hub/workflow.ts:487-564 runs on every transition and also calls writeStepResults().
Constraint from the transport

Every dispatch is wrapped by the awb hook's promptTemplate, fixed at workflow-creation time in createWorkflow hub/workflow.ts:594:

`You are the agent of a workflow in The Target Project named "${trimmed}".
This session is reused in order for every step of the workflow. Current step:

{{payload}}

Carry out the step and respond with the final result of that step.`

Two consequences. (a) A context-only turn will be framed to the agent as a task to carry out, so the context step's payload must explicitly say "this is background, do no work, acknowledge". (b) hub/awb.ts exports only createAwbHook hub/awb.ts:421 and deleteAwbHook hub/awb.ts:458 — there is no update path, and createAwbHook throws HookExistsError if the hook exists. Changing the template therefore only affects newly created workflows, so the plan must work under the existing template.

2.5 Step numbering, slugs and the on-disk results

  • hub/step-results.ts:43 — STEP_RESULTS_SUBDIR = ".target/steps", relative to the hook's workdir.
  • hub/step-results.ts:59-63 — stepResultFileName(step): 
    const position = String(step.orderIndex + 1).padStart(2, "0");
const slug = slugify(step.description).slice(0, 60).replace(/-+$/, "") || "step";
return `${position}-${slug}.md`;
    So the filename is derived from orderIndex and the description. Both change if a step is renumbered or reworded.
  • hub/step-results.ts:101-130 — writeStepResults() only writes; it never deletes. Any renumbering therefore leaves orphaned .md files behind that the agent will still read, because the pointer sentence in stepResultsNote() hub/step-results.ts:143 names the whole directory.
  • The live directory on this checkout confirms the format: .target/steps/01-investigate-…md … 04-merge-pr-…md.
This is why order_index 0 is the wrong choice

If the context step took order_index = 0, every existing task step shifts by one, 01-investigate-….md becomes 02-investigate-….md, and the old 01-… file stays on disk — the agent would then read two files claiming to be step 1 and 2 with the same content. order_index = -1 avoids the whole class of problem.

3. Recommended design

A single auto-managed, persisted step row of a new kind 'context', pinned at order_index = -1, owned by the hub rather than by the operator.

3.1 The shape

PropertyValueWhy
kind'context'New column, NOT NULL DEFAULT 'task', so every existing row upgrades to 'task'.
order_index-1Sorts first everywhere without renumbering anything (§2.5). Only one such row per workflow, enforced by the reconciler.
descriptionthe workflow's conversationContext (or a fixed marker when the context is images-only)Keeps composeStepInput's existing shape; the payload is still derived from contextPreamble, not from this field verbatim.
acceptance_criteriaNULL, alwaysThere is nothing to verify — the step's success condition is "the agent received it", which the result callback already proves. A judge pass here would burn a second turn to grade a paragraph of prose.
manual_reviewfalse, alwaysGating a human on the delivery of background text would stall every run for no decision.
use_subagentfalse, always, and exempt from the pressure overrideLoad-bearing. The point is for the background to live in the shared thread. Delegating it (SUBAGENT_SUFFIX, hub/runner.ts:53) would put the context inside a subagent that then exits. shouldForceSubagent hub/context-pressure.ts:75 must not be allowed to flip it either — though in practice the ratio is null on a fresh conversation.
max_retries / retry_interval_seconds0No judge, so no reject-and-retry cycle exists for it.
selectedforced 1 whenever at least one task step is selectedOtherwise nextPendingStep skips it (§2.6).

3.2 The lifecycle: one reconciler

A new exported function in hub/workflow.ts:

/** Creates, updates or removes the workflow's synthetic context step so it
 *  always agrees with the workflow's conversation context. Idempotent. */
export function reconcileContextStep(workflowId: string): Step | null

Rules, in order:

  1. If the workflow has neither conversationContext nor any field='context' attachment → delete any existing kind='context' row and return null. (Only when it is still pending; a context step that already ran is history and stays.)
  2. If workflow.contextInjected is true → do nothing. The background is already in the conversation; creating a pending step now would re-inject it. This is also what keeps legacy workflows safe (§8).
  3. Otherwise ensure exactly one kind='context' row exists at order_index = -1, status='pending', with description refreshed from the current context text.

Call sites — all existing functions, no new route needed:

  • setConversationContext() hub/workflow.ts:648 — text saved or cleared.
  • The attachment add/delete paths for field='context' — hub/server.ts:1024 and hub/server.ts:551 (or better, inside hub/attachments.ts' callers in workflow.ts).
  • startWorkflow() / resumeWorkflow() / restartWorkflow() hub/workflow.ts:969 / 1010 / 1033 — belt-and-braces, immediately after setStepSelection and (for restart) after setContextInjected(id,false).

3.3 The prompt the context step sends

composeStepInput hub/runner.ts:215 gains an early branch. For step.kind === "context" it returns the preamble and nothing else — no description images duplicated, no criteria note, no stepResultsNote (there are no prior results by definition), no subagent suffix — plus one sentence that survives the fixed hook template (§2.4):

Conversation context — this background applies to every step of this workflow:

<the context text>

<image list, if any>

---

This step exists only to establish that background for the rest of this
workflow. There is no work to do here: do not use any tools, do not delegate
anything, and do not start on any later step. Confirm in one line that you
have read and will apply the background above; the workflow's real steps
follow in separate turns on this same conversation.

Reusing contextPreamble() unchanged is deliberate — it already handles the images-only case and the compaction lead line.

3.4 What the guard means now

context_injected keeps its exact current meaning and its current writer (chainSession, hub/workflow.ts:620): the first session established for this workflow carries the context. With a context step that session is established by the context step's own callback, which is strictly more accurate than today — today the flag is set by whichever step happened to run first, whether or not the preamble was actually delivered. The freeze on editing (§2.1) and the injected badge in ContextPanel.tsx continue to work untouched.

3.5 Why this design over the others

  • It reuses the entire expensive half of the system: dispatch, session resume, started/result callbacks, timeouts, abort, the progress watchdog, the status file. The alternatives all rebuild some of it.
  • It gives the operator exactly what they asked for and can see: a real row, first in the list, with a status and a result, that ran automatically before step 1.
  • order_index = -1 makes it additive at the storage layer — no renumbering, no filename churn, no data migration of existing rows beyond a column default.
  • The blast radius is real but it is a finite, enumerable list of read paths (§2.6), each fixed by one WHERE kind = 'task' or one guard clause.

4. Alternatives considered

Alternative B — persisted context step at order_index = 0 rejected

Mechanically simpler to reason about ("it's just the first step"), but it renumbers every task step in every workflow that has a context. That breaks stepResultFileName hub/step-results.ts:59, orphans the old <NN>-<slug>.md files (writeStepResults never deletes), changes the numbers the operator sees in writeStatusMd hub/workflow.ts:522 and in target show hub/cli.ts:319, and forces a genuine data migration (UPDATE steps SET order_index = order_index + 1) that has to be exactly-once. All of that cost buys nothing that -1 does not already give.

Alternative C — a synthetic / virtual step, not persisted rejected

Attractive on paper: no schema change, no migration, nothing to delete. It does not survive contact with the callback pipeline. dispatchStep sends jobId: step.id and a callbackUrl containing step.callbackToken hub/runner.ts:319; markStepQueued, completeStep, markStepRunning are all UPDATE … WHERE id = ?; and onStepResult opens with const step = getStep(stepId); if (!step) return; hub/workflow.ts:1152-1153 — a virtual step's result callback would be silently dropped, leaving the workflow with no session id and no way to advance. Making it work means a parallel dispatch path, a parallel callback route, parallel timeout handling and a UI row with no id to hang actions off. That is strictly more new code than adding one column.

Alternative D — keep it at the transport layer, but emit it as its own turn rejected

The awb hook protocol is one input and one result callback per job: POST {jobId, input, callbackUrl, startedCallbackUrl} and the broker answers {ok:true} then calls back once hub/runner.ts:386-412. There is no way to send two turns within one job, so "its own turn" necessarily means "its own dispatch", which needs its own jobId and its own callback — i.e. a step row, which is Alternative A. Beyond that, this option fails the user's stated requirement in a softer way: a turn nobody can see in the step list is not "a separate step", it is the current behaviour with extra whitespace.

Alternative E — status quo (keep prepending) rejected

Worth stating what is actually wrong with it, since it does work: the background and step 1's task arrive as one indivisible instruction, so (a) 01-<slug>.md is named after step 1 but its conversation turn also contains the whole workflow's background; (b) a retry of step 1 (retryNote, hub/runner.ts:93) re-sends the task but the background is only in the compacted history; (c) a workflow whose first selected step is not step 1 still gets the preamble glued to whatever ran first, which reads oddly. These are the concrete symptoms the requested change fixes.

Design questions answered explicitly

  • Should the context step have an acceptance criterion? No. See §3.1. If a future operator wants one, it would have to be operator-authored, which contradicts "automatic".
  • What do judge steps do with it? Nothing — the judge is a phase of the step being judged hub/db.ts:35, and the context step never enters it because it has no criteria (onStepResult's if (!step.acceptanceCriteria) branch, hub/workflow.ts:1200).
  • Workflows with no context? No row is created; listSteps returns exactly what it returns today; composeStepInput's preamble is "" as before. Zero behavioural delta.
  • Does the context step re-run when a task step retries? No. Retries re-dispatch the same step id (beginRetry hub/db.ts:999); nothing re-opens a done step at -1.
  • Resuming a workflow mid-way? The context step is already done, so nextPendingStep passes over it and the run continues from where it stopped — which is correct, because the session it primed is the one being resumed.

5. Implementation plan

Phase 0 — Baseline

Prove the current behaviour before changing it.

  • Run npm test (root → npm --prefix hub test, i.e. node --test --import ./test-setup.ts) and npm run typecheck (hub + hub/ui). Record the pass counts.
  • Re-read hub/context.test.ts's assertions at lines 100-105 and 247-248 — they assert the current prepend shape and will be the tests that change meaning.

Phase 1 — Storage: the kind column

Make a context step representable. No behaviour change yet.

  • hub/db.ts
    • Add export type StepKind = "task" | "context"; next to StepPhase (~line 35).
    • Add kind: StepKind; to interface Step (~line 117) with a doc comment saying it is hub-owned, not operator-authored.
    • Add kind TEXT NOT NULL DEFAULT 'task' to the CREATE TABLE steps block (~line 281) and an addColumn("kind", "kind TEXT NOT NULL DEFAULT 'task'") next to the others (~line 337) so existing DBs upgrade.
    • rowToStep (~line 628): kind: (row.kind as StepKind) ?? "task".
    • insertStep (~line 661): accept kind?: StepKind and an explicit orderIndex?: number escape hatch (or a dedicated insertContextStep) so -1 can be written without going through the append/insert-after arithmetic. Persist kind in the INSERT column list.
    • stepProgress (~line 1262): add AND kind = 'task'.
    • setStepSelection (~line 1222): in the non-empty branch, selected = CASE WHEN id IN (…) OR kind = 'context' THEN 1 ELSE 0 END. Leave the empty branch alone — "select nothing" must still run nothing.
    • New helper getContextStep(workflowId): Step | null — WHERE workflow_id = ? AND kind = 'context'.

Phase 2 — Engine: materialise and dispatch it

The context step exists, runs first, and its payload is right.

  • hub/workflow.ts
    • New reconcileContextStep(workflowId) implementing the three rules in §3.2.
    • Call it from setConversationContext (line 648, after setWorkflowConversationContext, before writeStatusMd), from the context-attachment add/remove paths, and from startWorkflow/resumeWorkflow/restartWorkflow right after setStepSelection.
    • Guard the operator-facing mutators against a context step: editStep (line 735), removeStep (line 781), runStep (line 1432), forceStepStatus (line 385), continueStep (line 319) → throw new WorkflowError("the conversation-context step is managed by the hub"). Leave abortStep (line 1478) allowed — a hung context dispatch must be recoverable.
    • addStep (line 691): refuse afterStepId pointing at the context step (it would insert at 0 and shift every task step).
    • writeStatusMd (line 487): render the context step as a labelled line ("Conversation context — delivered / pending") rather than 0. [x] …, and keep the existing per-step loop over kind === 'task' only.
  • hub/step-results.ts
    • writeStepResults (line 101): filter out kind === 'context'. Its "result" is a one-line acknowledgement; writing 00-…md into .target/steps/ would add noise to the very directory the compaction-resilience feature asks the agent to trust.
  • hub/runner.ts
    • composeStepInput (line 215): early branch for step.kind === "context" returning contextPreamble(...) + CONTEXT_STEP_SUFFIX (§3.3). Export CONTEXT_STEP_SUFFIX so tests can assert on it.

Phase 4 — Optional follow-up (do not bundle with phases 1-3)

Unify compaction recovery with the context step.

Once the context step exists, compaction recovery could stop being a preamble on the next task step and instead reset the context step to pending, letting advance() re-dispatch it as its own re-priming turn (it is at -1, so it is picked first). That is conceptually cleaner and gives the operator a visible "re-primed after compaction" event. It is deliberately deferred because it changes an area with its own recently-landed test suite (hub/compaction.test.ts, hub/compaction-fixtures.ts) and because the detection happens inside dispatchStep (line 344), which is past the point where advance() chooses what to run — so it needs a small restructure, not a flag flip.

Phase 5 — Docs

  • docs/feature.md — requirement #2 currently says "prepended to the first dispatched step's input"; supersede it and add a status note.
  • README.md and web-docs/index.html — both describe the current injection.
  • hub/cli.ts — show (line 313) may want to print the context step separately now that orderIndex + 1 would print 0 for it (line 319).

6. Testing strategy

The harness that already exists is close to ideal for this. hub/context.test.ts:45-63 stands up a fake awb hook that records every dispatched input in order and answers {ok:true}, and finishStepOk (line 82) drives the real onStepResult path. Asserting "there are now two dispatches where there used to be one, and the first is the context" is a two-line change to that harness's expectations.

6.1 New / changed unit + integration tests

  • Ordering: a 2-step workflow with a context dispatches three inputs; inputs[0] matches /^Conversation context —/ and contains the "no work to do here" sentence; inputs[1] starts with step 1 and does not contain Conversation context.
  • No context → no context step: listSteps length is unchanged and the dispatched inputs are byte-identical to the pre-change baseline. This is the regression guard for the "strictly additive" claim.
  • Images-only context still produces a context step (mirrors the existing chainSession rule at hub/workflow.ts:632-634 and the assertion in hub/attachments.test.ts:393).
  • Idempotency: calling reconcileContextStep twice, and saving the same context text twice, yields exactly one kind='context' row.
  • Clearing the context (while not yet injected) deletes the pending context step.
  • Restart resets the context step to pending and re-dispatches it first, even when the operator restarted with only step 3 selected (this is the resetSteps/setStepSelection interaction from §2.6).
  • Resume mid-way does not re-dispatch a done context step.
  • Retry of a task step (judge rejects) does not re-dispatch the context step.
  • Progress: stepProgress for a 2-task workflow with a context reports total: 2, and the progress bar reaches 100% without the context step.
  • Immutability: PATCH/DELETE/run/status on the context step's id all return 400 (server-level, in hub/server.test.ts).
  • Subagent: the context step's input contains neither SUBAGENT_SUFFIX nor INLINE_SUFFIX nor CONTEXT_PRESSURE_SUFFIX and no stepResultsNote text.
  • Files: no 00-*.md appears in .target/steps/, and the existing steps' filenames are unchanged (the anti-renumbering guarantee).
  • Compaction: the existing hub/compaction.test.ts expectations must still hold — the re-injection preamble still lands on the next exec dispatch and is not doubled by the context step.

7. Risks & edge cases

These are the ones found in this code, not generic ones.

#RiskWhereMitigation
1 The context step is deselected and silently never runs. The UI sends an explicit id list to Start; setStepSelection deselects everything not in it, and nextPendingStep requires selected = 1. The workflow would run normally with the background silently missing. hub/db.ts:1222, 778 Force kind='context' selected in the non-empty branch of setStepSelection; assert it in a test.
2 Restart resets the guard but not the step. restartWorkflow sets context_injected = false and drops the session, but resetSteps only touches selected = 1 rows — an unselected context step stays done, so nothing re-primes the new conversation and the fallback prepend is now disabled. hub/workflow.ts:1044-1048, hub/db.ts:1243 Mitigated by risk 1's fix (always selected) plus an explicit reconcileContextStep call after the reset.
3 Filename renumbering / orphaned result files. Only bites if order_index = 0 is chosen: writeStepResults never deletes, so the old 01-…md would sit next to the new 02-…md with identical content, and the agent is explicitly told to trust that directory. hub/step-results.ts:59, 101 Use order_index = -1. Filter kind='context' out of writeStepResults.
4 Progress and the completion DM count a non-task. stepProgress is COUNT(*); notifyWorkflowCompleted reports steps.length. hub/db.ts:1262, hub/workflow.ts:838-848 AND kind='task' in stepProgress; filter the list in the notifier. (steps.at(-1) is already safe with -1.)
5 Two re-priming mechanisms. Compaction recovery re-prepends the preamble to the next exec dispatch. If the context step were also re-armed on compaction, the agent would get the background twice in two consecutive turns. hub/runner.ts:344-380, hub/compaction.ts:88 Phase 1-3 leave compaction recovery exactly as-is. Unification is Phase 4, on its own.
6 The hook template frames it as a task. Every payload is wrapped in "Current step: … Carry out the step and respond with the final result of that step" — and there is no way to update an existing hook's template (createAwbHook throws if the hook exists; no updater exists). hub/workflow.ts:594, hub/awb.ts:421-450 The context step's payload must itself say "no work to do here, do not use tools, acknowledge in one line" (§3.3). Never rely on changing the template.
7 Delegating the context to a subagent would defeat the feature. subagentInstruction always appends one of three suffixes, and shouldForceSubagent can override an inline step under context pressure. Background delivered inside a subagent dies with it. hub/runner.ts:83, hub/context-pressure.ts:75 No suffix at all for kind='context'; skip the pressure read entirely for it.
8 A failed context step fails the whole workflow. onStepResult's !outcome.ok branch sets the workflow failed, and advance's terminal derivation treats any failed step as workflow failure. hub/workflow.ts:1180-1195, 953 This is arguably correct (the background never landed, so every later step is running blind) — but it must be a deliberate decision, and the operator needs an obvious recovery. Abort stays allowed and a re-run path should exist (either allow ▶ on a failed context step, or have restart rebuild it).
9 Timeouts apply. The context step is a real dispatch, so findTimeoutCandidates / expireStale can time it out — including the queued timeout while it waits on the workdir flock behind another workflow. hub/db.ts:1171, hub/workflow.ts:141 Acceptable (it is one short turn), but note that this adds one more dispatch per workflow that can hit the queue.
10 afterStepId pointing at the context step. insertStep would compute orderIndex = -1 + 1 = 0 and shift every task step down — the exact renumbering the -1 choice exists to avoid. hub/db.ts:688-697, hub/workflow.ts:712-717 Reject it in addStep; the UI's "Add step after" only appears on a waiting step anyway (StepItem.tsx), which a context step never is.
11 Two extra turns of context budget. The context step adds one dispatch and one agent reply to the shared session, on top of the background text that was going to be sent anyway. Marginal, but the context-pressure feature exists precisely because this session's occupancy matters. hub/context-pressure.ts Keep the acknowledgement explicitly one line.
12 UI selection maths. allSelected, selectedCount and the Start-disabled rule all derive from the full steps array; leaving the context step in it makes "all selected" unreachable and the count wrong. hub/ui/src/views/WorkflowDetail.tsx:114-169, 244 Split contextStep out of steps before any selection state is computed.
13 Template import dedupe. POST …/steps/from-template dedupes by description against existing steps. A context step whose description holds the context text could theoretically collide with a template step's text. hub/server.ts:1241-1248 Build the existing-descriptions set from kind === 'task' steps only.

8. Migration

There is no row migration and no renumbering. The only schema change is one nullable-by-default column, added the same way every other late column in this file was:

addColumn("kind", "kind TEXT NOT NULL DEFAULT 'task'");   // hub/db.ts, ~line 337

Existing workflows fall into three buckets:

  1. No conversation context. Nothing happens, ever. No context step, no behaviour change.
  2. Context set but not yet injected (context_injected = 0). The next call to reconcileContextStep — triggered by the next context save, or by Start/Resume/Restart — materialises the step, and the run gets the new behaviour.
  3. Context already injected (context_injected = 1, mid-run). reconcileContextStep deliberately does nothing (rule 2, §3.2). The background is already in that conversation's history; fabricating a done context step would invent a run that never happened, and creating a pending one would re-inject. The workflow keeps its history, and gets a context step the next time it is restarted (which resets the flag and starts a fresh conversation anyway).
The safety valve

The old prepend path in composeStepInput/dispatchStep is not deleted. It is gated on "this workflow has no materialised context step" (Phase 2). So bucket 3, and any workflow where reconcileContextStep declined to act, keeps working exactly as it does today. The two mechanisms are mutually exclusive by construction, and the change can be rolled back by simply not creating context steps.

Rollback: dropping the feature means (a) stop calling reconcileContextStep, (b) delete any kind='context' rows. The column can stay — SQLite makes dropping it awkward and nothing reads it once no such rows exist.

9. Open questions / things I could not verify

Stated explicitly rather than guessed:

  • The awb broker's behaviour on a trivial turn. I read the hub's side of the protocol (hub/runner.ts, hub/awb.ts) but not vendor/agent-webhook-bridge itself. I have not verified how the broker handles a job whose agent reply is a single acknowledgement line, nor whether the free-code runner returns a session id for such a short run the same way claude does. If it does not, the context step would never chain a session and the workflow would stall — this should be smoke-tested against a real hook before Phase 2 is considered done.
  • hub/ui/legacy-index.html. It contains the string "Conversation context", but hub/server.ts serves the UI from hub/ui/dist (UI_DIR, line 130) and I found no reference to legacy-index.html anywhere in hub/server.ts or hub/ui/src. It looks like dead legacy markup, but I did not confirm that with the build config — check hub/ui/vite.config before deciding whether it needs the same copy changes.
  • The .code-graph index. There is a committed .code-graph/ directory and a recent commit "chore: refresh the .code-graph index". I did not inspect what generates it or whether adding a column/symbol requires regenerating it.
  • Exact line numbers will drift. Every reference in this document was read at ecbe391. The symbol names are the durable part.
  • Whether the operator should be able to re-run a failed context step with ▶. Risk 8 argues both ways and I did not find an existing convention for "hub-owned step that failed". This needs a product decision, not a code reading.
  • Precise UI copy and placement for the pinned row (inside the <ol> vs. above it) — a design call, not something the code dictates.
