1.Overview & Goals

The Target Project is a fully local web app (Node.js hub + React SPA) for defining and running agentic workflows. Today it has a single implicit operator: anyone who can open http://127.0.0.1:8893 sees every workflow, and a single shared adminToken gates mutations. This plan adds a single-user access layer — one account per machine, nothing more:

  • First-run setup (signup) — on a fresh install the UI offers a one-time setup screen: the user picks a password and receives a one-time recovery token, displayed exactly once with explicit "you must save this" instructions. Once the account exists, signup is disabled server-side and hidden in the UI; only the login screen is ever offered again.
  • Login — after authenticating, the user lands on the workflows screen and sees all local workflows. There is no per-user scoping: the login gate is the boundary.
  • Forgot password — the user enters their saved recovery token; if it matches, they set a new password and the token rotates (old token dies).
  • Lost password and lost token — there is deliberately no recovery path. The documented answer is a full local reset: stop the hub, wipe ~/.target/, restart, re-run first-run setup (§6.3). All workflow data is lost unless backed up first. Accepted risk (§11, R1).

Non-goals / constraints

  • Everything stays local: no remote server, no email, no external identity provider. Password recovery therefore cannot rely on e-mail — the saved token is the only recovery channel.
  • No multi-user anything: one account per machine; no owner columns, no per-user query filtering, no username registry, no per-user settings, no claim/assignment flows.
  • No new runtime dependencies (the hub deliberately uses zero native deps, SQLite via node:sqlite). All crypto uses Node's built-in node:crypto.
  • The existing agent/dispatch engine (hub/workflow.ts), awb callbacks and the CLI's direct-DB behaviour keep working during and after the change.
What got simpler vs. the previous multi-user draft Compared to the earlier multi-user version of this plan, the following was removed entirely: owner_id columns on workflows/templates and the index; all per-user WHERE owner_id = ? query scoping and 404-on-foreign-id checks; the username registry with case-insensitive uniqueness; the "claim legacy (un-owned) workflows" flow and its endpoint; per-user template visibility rules; and the out-of-band admin reset command. What remains is one singleton auth row, a small sessions table, a one-time setup screen, a password-only login, and the recovery-token mechanism — the user-facing behaviour (token shown once, rotation on reset) is unchanged.
Design principles Reuse the project's own patterns: additive SQLite migrations in hub/db.ts's open(), timing-safe comparisons as in hub/server.ts's isAdmin(), a thin typed API client in hub/ui/src/api/client.ts, and React views with CSS modules under hub/ui/src/views/.

3.Data Model

Exactly two new tables — a singleton auth row and a small sessions table — and zero changes to existing tables. Everything lands in hub/db.ts's open() as plain CREATE TABLE IF NOT EXISTS statements. No query that lists or fetches workflows/templates changes at all.

3.1 New table: auth (singleton)

A single-row table guarded by a CHECK constraint instead of a full users table with a uniqueness machinery: there is exactly one account, so the row is the account, and the row's existence doubles as the "setup completed" flag (SELECT 1 FROM auth — no separate flag to keep in sync). Decision D4

ColumnTypeNotes
idINTEGER PRIMARY KEY CHECK (id = 1)Singleton guard: any attempt to insert a second row violates the constraint. Setup inserts id = 1 and treats the constraint error as "setup already completed" (409).
display_nameTEXTOptional friendly name shown in the header; not a credential — login is password-only (§5, D6).
password_hashTEXT NOT NULLscrypt output, hex
password_saltTEXT NOT NULL16 random bytes, hex
recovery_token_hashTEXT NOT NULLSHA-256 of the recovery token (see §4.2); the plaintext token is never stored
recovery_token_set_atTEXT NOT NULLISO timestamp; rotation bookkeeping
failed_loginsINTEGER NOT NULL DEFAULT 0Rate-limit / lockout counter (single counter for the whole machine — there is only one account)
locked_untilTEXTTemporary lockout after repeated failures
created_at / updated_atTEXT NOT NULLISO timestamps, same convention as other tables

3.2 New table: sessions

A small sessions table (not a single active session) so the user can be logged in from two browsers or a browser plus a restored tab without kicking themselves out. No user_id column — every row belongs to the one account. Decision D5

ColumnTypeNotes
token_hashTEXT PRIMARY KEYSHA-256 of the opaque session token; the cookie carries the plaintext token, the DB only its hash — a DB dump cannot mint sessions
created_atTEXT NOT NULL
expires_atTEXT NOT NULLFixed cap: 30 days
last_seen_atTEXT NOT NULLSliding renewal: sessions idle > 14 days are treated as expired

3.3 Existing tables: no change (explicit simplification)

TableChangeRationale
workflows, templates, steps, attachments, settings none — no owner_id columns, no new indexes, no query changes Decision: with exactly one user, per-user data isolation is meaningless. After login the user sees every local workflow; before login the API simply doesn't serve data. The login gate replaces the entire owner-scoping layer from the previous draft (decision documented in §7).

3.4 On-disk layout (under ~/.target/)

  • Auth and session state live inside target.db — no new files needed. This keeps the single-file backup story (target.db + config.json) intact, and makes the full reset in §6.3 a single rm -rf ~/.target.
  • Existing per-workflow files (~/.target/<slug>-<id>.md, ~/.target/attachments/<workflowId>/, step results in each workdir) stay exactly where they are, untouched by this change. Decision D3

3.5 New data-layer module

A new hub/account.ts holds every auth/session function (mirroring how db.ts owns workflows): isSetupComplete, createAccount, getAccount, verifyAccountPassword, setAccountPassword, rotateRecoveryToken, verifyRecoveryToken, createSession, resolveSession, touchSession, deleteSession, deleteAllSessions. Password/token/session crypto helpers live in a sibling hub/auth.ts so the server and tests share them. Notably absent vs. the previous draft: no getUserByUsername, no listUsers, no claimUnownedWorkflows.

4.First-Run Setup (Signup)

Signup is a one-time setup step, not a standing endpoint. The moment the singleton auth row exists, the door closes permanently: the server rejects further setup attempts and the UI never renders the setup screen again.

4.1 Endpoints

MethodRouteAuthPurpose
GET/api/auth/statusopenReturns { setupCompleted: boolean } — drives the UI's choice between setup screen and login screen
POST/api/auth/setupopen only while no account existsBody { password, displayName? } → creates the singleton auth row, returns the one-time recovery token. Once the row exists: 409 {"error":"setup_already_completed"}, forever.
  • Validation: password ≥ 10 characters (local tool, but the DB holds the keys to every workflow — keep a real floor). displayName optional, ≤ 64 chars, display only. No username field — there is nothing to distinguish. Clear 400 errors per field.
  • Password hashing: crypto.scrypt(password, salt, 64) with a fresh 16-byte salt — memory-hard KDF built into Node, strictly better than the SHA-256+salt minimum and zero new dependencies. Decision D1
  • Atomicity: the insert relies on the CHECK (id = 1) singleton guard (§3.1), so even two simultaneous setup requests cannot create two accounts — the loser gets a constraint error mapped to 409.

4.2 Recovery-token generation & display (the core product requirement — unchanged)

  1. Server generates 128 bits of entropy: crypto.randomBytes(16), formatted for humans as four groups: XXXX-XXXX-XXXX-XXXX (Crockford base32, no ambiguous characters like 0/O, 1/l).
  2. Server stores only SHA-256(token) in auth.recovery_token_hash (a fast hash is correct here — the token has 128 bits of entropy, so brute force is infeasible; hashing prevents a DB read from becoming an account takeover). The plaintext leaves the server only in the setup HTTP response. Decision D2
  3. UI moves to a dedicated "Save your recovery token" step — a full modal screen that cannot be dismissed accidentally:
    • The token rendered large, monospace, with a copy-to-clipboard button and a "Download as .txt" button.
    • Prominent warning copy: "This token is shown once and never stored in readable form. It is the ONLY way to reset your password. If you lose both your password and this token, the only recovery is wiping all Target data on this machine and reinstalling (see docs). Save it somewhere safe (password manager or printed)."
    • A mandatory checkbox "I have saved my recovery token" gating the Continue button.
  4. UI confirms (Continue) → the token is wiped from component state; the user is signed in automatically (a session is issued as in login) and lands on the workflows screen — where all pre-existing local workflows are already visible (§8).
  5. Server never returns the token again. GET /api/auth/me exposes only recoveryTokenSetAt so the UI can show "recovery token created on …" without revealing it.
Edge case If the setup response is lost (browser crash between steps 2 and 3), the account exists but the user never saw the token. Mitigation: if the user never confirms the token step, the account's first login triggers a one-time "regenerate recovery token" prompt (old hash is replaced, new token shown once). Regeneration always requires a valid password or a valid old token.
After setup completes GET /api/auth/status returns { setupCompleted: true } and the UI routes to the login screen on every subsequent load. The setup screen is unreachable — there is no "create another account" path anywhere in the product.

5.Login Flow & Session Management

5.1 Endpoints

MethodRouteAuthPurpose
POST/api/auth/loginopenVerify password, issue session cookie, return the public account object
POST/api/auth/logoutsessionDelete the session row, clear the cookie
GET/api/auth/mesession{ displayName, recoveryTokenSetAt }; drives the UI's route guard

5.2 Login sequence

Password-only login: the login form is a single password field. With exactly one account, a username adds friction but zero selectivity — the optional display_name is shown in the header after login, never asked for as a credential. Decision D6

  1. UI posts { password } to /api/auth/login.
  2. Server loads the singleton auth row, checks locked_until, then scrypt-verifies the password with crypto.timingSafeEqual. Failure → increment failed_logins; after 5 consecutive failures, lock for 5 minutes (exponential on repeat). Uniform 401 {"error":"invalid_credentials"} for every failure mode.
  3. Server on success: reset counters, create a session — 32 random bytes as the token, store only SHA-256(token) in sessions, set expires_at = now + 30d.
  4. Server responds with Set-Cookie: target_session=<token>; HttpOnly; SameSite=Strict; Path=/; Max-Age=2592000 and the public account JSON. HttpOnly keeps the token out of JS reach (XSS exfiltration); SameSite=Strict blocks CSRF; Secure is omitted only because the hub serves plain HTTP on 127.0.0.1 — noted in §9.
  5. UI receives the account object, switches App.tsx to the authenticated shell and renders the workflows screen with all local workflows — the same unfiltered list the hub serves today.

5.3 Session resolution on every request

  • A small resolver in hub/server.ts (replacing/extending isAdmin()): read the target_session cookie → hash → resolveSession(hash) → check expiry + idle window (last_seen_at older than 14 days ⇒ expired) → touchSession (throttled to one write per minute per session) → request is authenticated.
  • All existing /api/workflows*, /api/templates*, /api/settings*, /api/conversations*, /api/fs/*, /api/attachments* routes require a resolved session or a valid admin Authorization: Bearer (transition period for scripts/automation, §11 Q1). Unauthenticated ⇒ 401 {"error":"login_required"}.
  • awb callbacks (/api/steps/:id/started|result) keep their per-step token — they are machine-internal and unaffected.
  • The UI's client.ts adds credentials: "same-origin" and stops needing the admin token for day-to-day use; the existing Bearer path stays for scripts/legacy flow during transition.

5.4 Logout & lifecycle

  • Logout deletes the session row (server-side invalidation, not just cookie clearing) and sets an expired cookie. Other concurrent sessions (second browser) stay valid — "log out everywhere" happens automatically on password reset via deleteAllSessions.
  • Lazy cleanup: expired sessions are deleted opportunistically on resolveSession — same "lazy expiry" philosophy the codebase already uses for step timeouts (no timers, survives restarts).

6.Password Reset & Full Local Reset

No e-mail exists in this system — the recovery token saved at setup is the only recovery channel. When it is gone too, the only remaining procedure is a full wipe (§6.3).

6.1 Endpoint

MethodRouteAuthPurpose
POST/api/auth/password/resetopen, rate-limitedBody { recoveryToken, newPassword } → verify token, set new password, rotate token, kill all sessions

No username field — the token is checked against the singleton auth row.

6.2 Sequence

  1. UI — "Forgot password" link on the login screen opens ResetPasswordView: recovery token + new password ×2.
  2. Server normalizes the token input (strip spaces/dashes, uppercase) and computes SHA-256; compares against recovery_token_hash with crypto.timingSafeEqual.
  3. Server on match, in one transaction:
    • re-hash newPassword with a fresh salt → password_hash/password_salt;
    • rotate the recovery token: generate a new one, store its hash — the old token is dead (a used token that leaked can't be replayed);
    • delete all sessions (deleteAllSessions) — force re-login in every browser;
    • reset failed_logins/locked_until.
  4. Server responds with the new recovery token, shown exactly once — same display treatment as setup §4.2 (copy/download + "I saved it" checkbox).
  5. UI then routes to login (or logs the user in directly with a fresh session — product decision, default: fresh session for less friction).
Abuse control The reset endpoint is open by design, so it gets the strictest rate limiting in the app: a per-IP counter, 5 attempts ⇒ 15-minute hold, exponential thereafter. With 128-bit tokens this is defense-in-depth.

6.3 Lost password and lost token — full local reset (no recovery by design)

If the user loses both credentials there is intentionally no recovery mechanism — no admin reset command, no backdoor, no support flow. The documented procedure is a full local reset:

  1. Operator stops the hub: Ctrl+C the daemon, or lsof -ti :8893 | xargs kill (equivalently pkill -f "node daemon.ts").
  2. Operator optionally backs up what can be saved: cp -a ~/.target ~/.target-backup-$(date +%F). (Also $TARGET_HOME if the install overrides the default location.)
  3. Operator deletes the state directory: rm -rf ~/.target.
  4. Operator restarts: npm start. The hub recreates an empty ~/.target/ (fresh config.json with a new adminToken, empty target.db).
  5. UI shows first-run setup again (setupCompleted: false) — the operator picks a new password and saves a new recovery token, as in §4.
Data loss warning Wiping ~/.target/ destroys everything: the workflows/steps/templates database, attachments, per-workflow progress files, settings, and the account itself. Step-result files under each workdir's .target/steps/ survive, but the hub no longer knows the workflows they belonged to. Back up before wiping if any of it matters. This is an accepted product risk (§11, R1).
Why no admin reset command The previous draft included an out-of-band node hub/users.ts reset maintenance command. It is removed: a standing command that re-issues credentials without the old password or token is a permanent backdoor, and anyone with shell access can already wipe ~/.target/ anyway. Keeping exactly one documented escape hatch — the wipe — makes the security story honest and the code smaller.

7.Data Access After Login

There is no per-user data isolation — this section exists to document that as an explicit decision, replacing the entire owner-scoping design of the previous draft.

Decision Access control is a single binary gate at the request layer: unauthenticated ⇒ 401 login_required; authenticated ⇒ full read/write access to every workflow, template, attachment, conversation and setting on the machine. No owner_id columns, no WHERE owner_id = ?, no 404-on-foreign-id checks, no "legacy/unclaimed" state. The data layer's existing queries are byte-for-byte unchanged.

7.1 Query layer (hub/db.ts)

  • listWorkflows, getWorkflow, listTemplates, step/attachment lookups: no signature or SQL changes.
  • Route handlers in hub/server.ts gain exactly one line of behaviour: run the session resolver (§5.3) before touching the DB. Nothing else.
  • settings stays machine-global — trivially correct when there is one user.

7.2 Engine behaviour (hub/workflow.ts, hub/runner.ts)

  • The dispatch engine is completely untouched: it never participated in auth and still doesn't.
  • A running workflow keeps running if the user logs out — sessions gate API access, not process lifetime. Documented behaviour.

7.3 UI changes

  • App.tsx: on load, call GET /api/auth/status. setupCompleted: false ⇒ render SetupView (§4). Otherwise call GET /api/auth/me: 401 ⇒ render the login/reset stack; 200 ⇒ render the existing shell unchanged.
  • Header.tsx: show the display name (if set), and a Logout button. That is the entire header diff — no claim affordances, no legacy sections.
  • No per-view changes: list/detail/templates already render server data, and the server data is the same as today.

8.Migration Plan for Existing Data

Existing installs have workflows, steps, templates and attachments — and after upgrade they simply belong to the machine's single user. There is no claiming, no assignment, no NULL-owner limbo: the data migration is a no-op.

8.1 Schema migration (automatic, on hub start)

  • open() gains two CREATE TABLE IF NOT EXISTS statements (auth, sessions). No ALTER TABLE on any existing table — the simplest possible migration under the project's own additive pattern. Rollback-safe by construction: older code ignores the two new tables entirely.

8.2 Data migration (none — and what upgrade day looks like)

  1. Hub starts after upgrade; auth is empty ⇒ GET /api/auth/status returns { setupCompleted: false }.
  2. UI shows the first-run setup screen (§4). The user sets a password, saves the recovery token, and is logged in automatically.
  3. Rule — the moment setup completes, every pre-existing workflow, step, template and attachment is simply visible and usable after login. Existing local data belongs to the single user by definition; there is nothing to assign and no UI for assigning it.
  4. On-disk files — nothing moves and nothing is renamed: ~/.target/*.md, ~/.target/attachments/ and workdir .target/steps/ are keyed by workflow id/slug, which this change never touches. Decision D3
Mid-run safety A workflow that is running during the upgrade keeps running: the engine never consults the auth/sessions tables mid-dispatch, and no existing row is modified by the migration. The only new behaviour on upgrade day is that /api routes start answering 401 until setup + login are completed once.

9.Security Considerations

AreaMeasure
Password storagescrypt (N=16384, r=8, p=1 — Node defaults) with a 16-byte salt; hex-encoded. Never logged, never returned by any endpoint. Plaintext passwords exist only in request memory.
Recovery token128-bit entropy, SHA-256-hashed at rest, shown exactly once, rotated on every successful reset and on regeneration. Timing-safe comparison. Losing it together with the password ⇒ full wipe (§6.3), accepted risk R1.
Session tokens256-bit opaque tokens; DB stores SHA-256(token) only. HttpOnly + SameSite=Strict cookie; 30-day cap, 14-day idle expiry; server-side deletion on logout (single session) and on password reset (all sessions).
Comparisonscrypto.timingSafeEqual everywhere a secret is compared (extends the pattern already used by isAdmin()).
Brute forceOne counter on the singleton auth row (failed_logins/locked_until) for login, plus a per-IP counter for password/reset: 5 failures ⇒ 5–15 min lockout, exponential. Uniform invalid_credentials errors. Simpler than the previous draft: no per-username tracking, because there is only one account.
Setup endpointPOST /api/auth/setup is open only while auth is empty; the singleton CHECK (id = 1) constraint makes double-setup impossible even under a race. Afterwards it is a permanent 409.
Network postureHub already binds 127.0.0.1 only — keep it. Document that exposing the port (SSH tunnel, reverse proxy) requires adding TLS + the Secure cookie flag before sessions are safe there.
XSS / injectionReact escapes by default; all SQL stays parameterized (node:sqlite prepared statements, as today). Token rendered as text, never interpolated into HTML.
AuthorizationOne session gate in front of all /api routes except /api/auth/* and the awb per-step-token callbacks (unchanged). No object-level checks — there is only one user.
Local threat modelHonest boundary: anyone with read access to ~/.target/target.db or the machine's shell can bypass app-level auth (and could already today — including wiping the state directory, §6.3). The subsystem protects the app from casual local snooping and unauthorized browser access, not against a hostile local admin. Stated plainly in docs (§11, R3).
Admin tokenadminToken remains as a bootstrap/automation credential during transition (§11 Q1); config file permissions (chmod 600 recommendation) documented. A wipe regenerates it.

10.Implementation Phases / Task Breakdown

Ordered checklist. Every item references the real path it touches. NEW = create, MOD = modify.

Phase 1 — Data layer & crypto (backend foundation)
  • MOD hub/db.ts — add auth (with CHECK (id = 1) singleton guard) + sessions tables to open() via CREATE TABLE IF NOT EXISTS. No other schema change — no ALTER TABLE, no owner columns, no new indexes, no changes to Workflow/Template interfaces or existing queries.

  • MOD hub/server.ts — cookie parsing helper; session resolver (session OR admin bearer during transition); new routes: GET /api/auth/status, POST /api/auth/setup (409 once complete), POST /api/auth/login, POST /api/auth/logout, GET /api/auth/me, POST /api/auth/password/reset; rate limiting on auth endpoints.
  • MOD hub/server.ts — put the resolver in front of every existing workflow/template/attachment/conversation/fs route; unauthenticated ⇒ 401 login_required. No handler body changes (no ownership checks — §7).
  • MOD hub/server.test.ts (+ new hub/auth-routes.test.ts) — status/setup/login/logout/reset happy paths, setup-already-completed 409, 401s on gated routes, lockout, token rotation on reset, session purge on reset.

Phase 3 — UI: auth screens + session plumbing
  • MOD hub/ui/src/api/client.ts + hub/ui/src/api/types.ts — credentials: "same-origin"; new auth API group (status/setup/login/logout/me/reset); Account type; keep admin-token helpers for transition.

  • MOD hub/ui/src/App.tsx — auth gate via GET /api/auth/status + GET /api/auth/me; route between setup / login / reset and the existing shell.

Phase 4 — Rollout & hardening
  • Verify upgrade path on a copy of a real ~/.target/: status flips to setup-completed after first-run setup, all pre-existing workflows visible after login, mid-run workflow unaffected.
  • Verify the wipe-and-reinstall procedure end-to-end (§6.3) on a throwaway TARGET_HOME: stop → rm -rf → restart → setup screen returns.
  • Security pass: cookie flags, rate-limit counters surviving restart (they live in the DB row), uniform errors, token rotation on reset, session purge on logout/reset, setup race ⇒ 409.
  • MOD docs/ — new "Access & authentication" doc (first-run setup, login, recovery token, full local reset incl. data-loss warning, threat model); update architecture notes mentioning adminToken-only auth.
  • MOD README.md — first-run experience now starts at the setup screen.
  • Full suite green: npm test + npm run typecheck.

  1. Q1 — Admin token endgame. Keep adminToken indefinitely as an automation credential alongside sessions, or retire it once sessions stabilize (breaking existing scripts that use Bearer)?
  2. Q2 — Legacy UI. hub/ui/legacy-index.html predates the React SPA. Retire it, or also add a login gate there?
  3. Q3 — Password-only login confirmation. Plan assumes a single password field (D6) with an optional display name that is never a credential. Confirm, or keep a cosmetic username field for habit/familiarity?
  4. Q4 — Headless installs. Should the CLI offer a non-interactive first-run setup (env var / flag) for machines where a browser isn't practical, or is the web setup screen the only path?
  5. Q5 — Concurrent sessions. Plan allows a small sessions table so two browsers stay logged in (D5). Acceptable, or should a new login invalidate the previous session (single active session)?

Risks

  1. R1 — ACCEPTED: lost token + lost password ⇒ full reinstall with data loss. There is deliberately no recovery path beyond the token. The user must stop the hub, wipe ~/.target/, and re-run first-run setup; all workflows, templates, attachments and settings are lost unless backed up beforehand (§6.3). The one-time-display flow (copy + download + mandatory checkbox, with this consequence stated in the warning copy) is the mitigation.
  2. R2 — GET routes become authenticated. Any external script polling GET /api/workflows anonymously breaks on upgrade. Mitigation: admin Bearer keeps working during transition; note in changelog/docs.
  3. R3 — Local threat model. App-level auth does not stop someone with shell/filesystem access (DB is readable, workdirs are shared machine paths, "open terminal" spawns real shells, and the §6.3 wipe is itself unauthenticated by necessity). Docs must state this plainly; the app gate protects against casual browser-level access only.
  4. R4 — Recovery-token UX. Users will lose tokens. With no e-mail channel, the only softer landings are the signup/reset display treatment and the regeneration prompt after a lost setup response (§4.2 edge case). Beyond that, R1 applies — that trade-off is the product decision.
